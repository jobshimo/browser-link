# Lab 2026-11-21: downloads on cdp-direct (experiments E1-E5, gap G9)

Experiments E1-E5 of [`docs/design/cdp-direct-parity.md`](../../../../docs/design/cdp-direct-parity.md) (section 6), asked before P8 (G9, `browser.download` selector mode on `cdp:` tabs) and owner decision D17. Built from `main` at e59ae74 (release 1.4.42). No product code was changed.

Follows the convention of `2026-11-20-cdp-direct-browser-socket/` (X3). The four `chrome-*.txt` files are the verbatim stdout of one run each and are never edited.

## Question

E1: do `Page.setDownloadBehavior` / `Browser.setDownloadBehavior` with `allow` and a path succeed on a page-target socket (and the browser socket), headless and headed, on 118 and stable, and do they suppress "Ask where to save each file"? E2: what is the scope of the setting (tab, browser context, browser), and does it revert when the socket that set it closes, normally or abruptly, or when the process holding it is killed? E3: the fields of `Page.downloadWillBegin` / `downloadProgress` (and the `Browser.*` twins), which socket gets which, and whether downloads from a new window, a cross-origin iframe and a service worker reach the clicked tab's session. E4: `post`, `one-time`, `chunked`, `gzip` under `allow` and `deny`. E5: two concurrent downloads of the same URL.

## Method

No MCP server is needed and none was started. The script launches Chrome with its own temporary profile under one `mkdtemp` directory in the OS temp dir (printed as `scratch=` at the top of each file and as `<scratch>` in plain-text lines; inside JSON the path appears in full because the replace does not match JSON-escaped backslashes) and a free remote-debugging port. Before launch it writes the profile's `Default/Preferences` with `download.prompt_for_download: true` and `download.default_directory` = `<scratch>/chrome-default-dir`; both files show Chrome kept the setting (`profile Preferences on disk after exit: download={...,"prompt_for_download":true}`). Sockets are the server's own `CdpClient` (`packages/server/dist/cdp/client.js`): page sockets dial `/devtools/page/<id>` and send `Target.getTargetInfo` + `Page.enable` as `transport.ts` `dial` does; browser sockets dial the `webSocketDebuggerUrl` of `/json/version`. Every setting is done on its own socket, separate from the clicking socket `page-T1`, so closing it tests revert.

A **trial** points `#dl` at a unique URL, clicks it with `Page.bringToFront` + three `Input.dispatchMouseEvent`s, then watches every staging dir and the profile's default dir until a finished file appears (or 2-4 s), and prints every `*download*` and `Target.*` event each open socket received. A file lands in the staging dir of the setting in force, so "where it landed" identifies which setting applied. File bytes are compared with the served bytes (`report-bytes`, `reversed-bytes(2nd request)`).

**How "prompt suppressed" was determined.** Headless has no Save-as UI: with nothing set, the download is cancelled at once (the baseline). Headed, the script lists the visible top-level windows of every process in Chrome's process tree (Win32 `EnumWindows` over the browser pid and its descendants, `Win32_Process` parent links) about one second after each trial. With nothing set, a `Save As [class #32770, child process]` window appears and the download stays `inProgress` with all bytes received and no file; with `allow`, no such window appears and the file is in the staging dir. That pair is the evidence.

The process-kill case (E2.e/f) runs a child `node g9-downloads.mjs --child <ws> Browser.setDownloadBehavior <dir>` that sets `allow` on a page socket of T1, prints `SET`, and is then killed with `SIGKILL` (Windows `TerminateProcess`). The "abrupt close" case calls `ws.terminate()` (TCP destroyed, no close frame).

Two harness lessons from draft runs (not recorded): a tab that is not in front does not act on a dispatched click until a later click elsewhere, so every click brings its tab to front first; and the initial `about:blank` document also reports `readyState` `complete`, so tabs wait for the fixture URL.

The owner primary was not running during the runs (`owner primary: none was running` in every file); no file reached the owner's real Downloads folder (`owner's real Downloads folder holds g9-* files: none` in every file).

## Observations

Every quote is from the raw files. Where Chrome 118 and 157 differ it says so; otherwise the lines are the same in both (a normalized diff of the two headless files differs only in the lines named below).

### E1. `allow` + path works on a page socket, both Chromes, headless and headed; it suppresses the Save-as prompt

- **Accepted on a page socket.** Both `Page.setDownloadBehavior` and `Browser.setDownloadBehavior` answer `{}` on a page socket and the file lands in the given dir (both files):
  ```
  [setter-page-Page] Page.setDownloadBehavior {"behavior":"allow","downloadPath":"<scratch>\\stage-e1-1"} -> {}
  landed: stage-e1-1/g9-e1-1.bin (2048 B, report-bytes)
  [setter-page-Browser] Browser.setDownloadBehavior {"behavior":"allow",...,"eventsEnabled":true} -> {}
  landed: stage-e1-2/g9-e1-2.bin (2048 B, report-bytes)
  ```
  On the browser socket `Browser.setDownloadBehavior` works (`landed: stage-e1-3/g9-e1-3.bin`) and `Page.setDownloadBehavior` does not exist: `FAILED: 'Page.setDownloadBehavior' wasn't found` (both).
- **Prompt suppressed (headed, both).** With `allow` set by any of the three working forms the file landed and no dialog window was listed, e.g. stable: `landed: stage-e1h-1/g9-e1h-1.bin (2048 B, report-bytes)` then `visible windows of Chrome's process tree: [class Chrome_WidgetWin_1, browser process] | Recent download history [class Chrome_WidgetWin_1, browser process] | g9 downloads - Google Chrome [...]`. After the setting sockets closed, the same click gave `landed: NOTHING` with `states inProgress ... "receivedBytes":2048,"state":"inProgress"` and `Save As [class #32770, child process]` (118 and stable). "Recent download history" (the download bubble) is shown after an `allow` download in both headed files: the user sees that a download happened.
- **Baseline headless (both).** Nothing set, profile asking: `Page.downloadProgress ... states inProgress>canceled ... "receivedBytes":0,"state":"canceled"` and `landed: NOTHING`.
- **Behavior values.** `deny`, `allow` (needs a path: `FAILED: downloadPath not provided`), `allowAndName` and `default` behave as documented. **`hold` and `pending` (not in the documented set) answer `{}` on both Chromes** on every method that exists, and a download then is cancelled like the baseline (`E1.8b "hold"` and `E1.8c Page "hold"`: `states inProgress>canceled`, `landed: NOTHING`). So no CDP value holds a download pending a later decision; unknown values are silently accepted and act like `default` here (headless).
- **Differences.** `allowAndName` with no path: 118 `-> {}`, 157 `FAILED: downloadPath not provided`. `browserContextId` = the default tab's own context id: 118 `FAILED: Failed to find browser context for id <id>` (on both sockets), 157 `-> {}` (the same split X3 saw for `Browser.setPermission`).
- **Path handling (both).** A relative `downloadPath` answers `{}` (no download was tried with it). A missing absolute dir is created: `landed: stage-e1-missing/deeper/g9-e1-missing.bin`, `the missing dir exists now: true`. `allowAndName` names the file by guid: `landed: stage-e1-name/<guid>`.
- **Which socket gets which event (both).** `Browser.downloadWillBegin`/`Browser.downloadProgress` arrive only on the socket that sent `Browser.setDownloadBehavior` with `eventsEnabled: true` (when that is a page socket it gets both the `Browser.*` and the `Page.*` events). `Page.downloadWillBegin`/`Page.downloadProgress` arrive on every page socket of the tab with `Page.enable`, whatever the behavior, including the baseline and `deny`. With `eventsEnabled` omitted (`E1.9`) no `Browser.*` event appears.

### E2. Scope is the browser context; the setting reverts when the setting socket closes, terminates, or its process dies

- **Scope = browser context, for all three forms (both).** Set on a page socket of T1 (`Page.` or `Browser.setDownloadBehavior`) or on the browser socket without a context: T1 and T2 (another tab of the default context) land in the stage (`landed: stage-e2a/g9-e2a-T2.bin`, `stage-e2b/g9-e2b-T2.bin`, `stage-e2c/g9-e2c-T2.bin`); T3 in a context from `Target.createBrowserContext` does not (`click in T3 (other browser context)`: `landed: NOTHING`, `"state":"canceled"`). With `browserContextId` = that context on the browser socket only T3 goes to the second stage (`landed: stage-e2c-ctxC/g9-e2c-ctxC-T3.bin`) while T1 keeps the first (`landed: stage-e2c/g9-e2c-ctxC-T1.bin`). `Page.setDownloadBehavior` is not tab-scoped.
- **Revert on close, every way tested (both).** After the setting socket closed normally (`e2a`, `e2b`, `e2c` "after close"), after `ws.terminate()` (`e2d after terminate`), and after the process holding the socket was killed (`e2e after the child was killed`), the next click in T1 is the baseline: `landed: NOTHING` with `"receivedBytes":0,"state":"canceled"`. Headed, both Chromes, after normal close and after terminate: `Save As [class #32770, child process]` (the terminate trial ran while the dialog of the previous trial was still open, so only one dialog is listed; the download itself stayed `inProgress` with no file).
- **A download in flight when the setting process dies completes into the stage (both).** The child set `allow`, a 3-second download started, the child was killed ~800 ms later: `during the download, before the kill: ["stage-e2f-inflight/g9-e2f-inflight.bin.crdownload"]`, then `landed: stage-e2f-inflight/g9-e2f-inflight.bin (2048 B, report-bytes)`, `states inProgress>completed`. The path is fixed when the download starts.
- **Who resets (both).** A quiet page socket (only `getTargetInfo` + `Page.enable`) closing does not reset A's setting (`landed: stage-e2g-A/g9-e2g-after-quiet.bin`). A socket X that set **another** context closing resets only that context (`after X (set ctxC) closed: click in T1` lands in `stage-e2g-A`; `click in T3` is `canceled`). **Two sockets on the same context: the last set wins, and when the later one closes the context is reset to default even though the earlier one is still open**: `e2h A then B set the default ctx` → `landed: stage-e2h-B/g9-e2h-both.bin`; `after B closed (A still open)` → `landed: NOTHING`, `"state":"canceled"`. A keeps receiving `Browser.downloadWillBegin` for that cancelled download, so its `eventsEnabled` survives while its behavior does not.

### E3. Field sets; every class reaches the browser-level events, only same-frame classes reach the tab's page socket

- **Fields (both).** `Page.downloadWillBegin` and `Browser.downloadWillBegin`: `{"frameId","guid","url","suggestedFilename"}`. `Page.downloadProgress`: `{"guid","totalBytes","receivedBytes","state"}` with `state` `inProgress`, `completed`, `canceled`. `Browser.downloadProgress`: the same, and **on 157 the `completed` event adds `"filePath"`** (e.g. `"state":"completed","filePath":"<scratch>\\stage-e3\\g9-e3-slow.bin"`); 118 has no `filePath`. The `guid` is the same in both domains and is the file name under `allowAndName`. Progress is reported in steps (`E3.2`: `receivedBytes` 0, 0, 1024, 1792, 2048, then `completed`).
- **New window (both).** A `target=_blank` link and `window.open` to an attachment: `Target.targetCreated` with `"openerId":"<T1 targetId>"`, then `Browser.downloadWillBegin {"frameId":"<the NEW target's id>",...}`, then `Target.targetDestroyed` of that target 7 to 10 ms after the `downloadWillBegin` (e.g. 118: `+  41ms Browser.downloadWillBegin`, `+  51ms Target.targetDestroyed`). **No `Page.downloadWillBegin` on T1's page socket.** The file landed in the stage (`stage-e3/g9-e3-newwin-link.bin`, `g9-e3-newwin-open.bin`).
- **Cross-site iframe (both).** The iframe is an out-of-process target (`iframe targets now: [{"targetId":"...","type":"iframe",...}]`; T1's `Page.getFrameTree` has no child frames: `T1 frame tree: undefined`). A click inside it: `Browser.downloadWillBegin {"frameId":"<the iframe target id>",...}` only; **no `Page.downloadWillBegin` on T1's page socket.** The iframe target's parent: 157 lists `"parentId":"<T1 targetId>","parentFrameId":"<T1 targetId>"`; **118 lists neither field**.
- **Service worker (both).** A download whose response the service worker made (`served for /sw-dl (0 = the service worker answered): {}`): `Page.downloadWillBegin` on T1's page socket with `"frameId":"<T1 main frame>"` and the same on the browser socket; it landed (`stage-e3/g9-e3-sw.bin`).
- **`blob:` + `download` attribute, programmatic `a.click()` (both).** Reported on T1 (`"url":"blob:http://127.0.0.1:.../...","suggestedFilename":"g9-e3-blob.bin"`), `totalBytes":16`, landed.

### E4. post, one-time, chunked, gzip: one request each, correct bytes under `allow`; cancelled under `deny`

- **`allow` (both).** `landed: stage-e4/g9-e4-post.pdf (2048 B, report-bytes)` with `served: {"/post.pdf?k=allow":{"requests":1,"methods":["POST"]}}`; the one-time token `requests":1` and `report-bytes`; chunked `report-bytes` with `totalBytes":2048` at `completed`; gzip saved decoded (`g9-e4-gzip-allow.bin (2048 B, report-bytes)`, not `gzip-bytes(still-encoded)`). Chrome made exactly one request per download in every case and the page did not navigate (`T1 url now: http://127.0.0.1:.../`).
- **`deny` (both).** Each still sends its one request (`served: {"/post.pdf?k=deny":{"requests":1,"methods":["POST"]}}`, same for the others), reports `Page.downloadWillBegin`, then `states inProgress>canceled`, nothing lands. A one-time URL is consumed by a denied download. Chunked and gzip report `"totalBytes":0` at cancel.

### E5. Two downloads of the same URL: two guids, one file under `allow`; two files under `allowAndName`

- **`allow`, same tab twice and T1 + T2 at once (both).** Two `downloadWillBegin` with distinct guids, two `completed`, two requests served, **one file**: `landed: stage-e5a/g9-e5-same.bin (2048 B, reversed-bytes(2nd request))` and `stage-e5b/g9-e5-two-tabs.bin (2048 B, reversed-bytes(2nd request))`. On 157 both `completed` events carry the same `filePath` (`...\\stage-e5a\\g9-e5-same.bin` twice). The bytes of the first download are lost without any error event.
- **`allowAndName` (both).** Two files named by guid, each with its own bytes: `stage-e5c/<guid1> (2048 B, report-bytes)`, `stage-e5c/<guid2> (2048 B, reversed-bytes(2nd request))`, and on 157 each `completed` `filePath` is its own guid path.
- **Attribution (both).** Each `downloadWillBegin` carries the clicking tab's `frameId` (T1's or T2's) on that tab's page socket and on the browser socket, so two tabs downloading one URL are told apart by `frameId`; two downloads in the same tab are told apart only by `guid`.

## What this means for D17 (facts only; the decision is the owner's)

- There is no CDP behavior that holds a download for a later decision on either Chrome: the documented values are `deny`, `allow`, `allowAndName`, `default`, and an unknown value such as `hold` is accepted with `{}` and acts like the default (headless).
- `allow`/`allowAndName` with a path is accepted on the page socket the server already holds (both `Page.` and `Browser.setDownloadBehavior`), on 118 and 157, headless and headed, and suppresses the Save-as prompt of a profile that asks. The download bubble still shows.
- The setting covers the whole browser context of the tab (the user's default context: every tab), not the clicked tab. While it is set, every download the user makes in any tab of that context goes to the staging dir without a prompt.
- It reverts to the user's behavior when the socket that set it closes, is terminated, or its process is killed; a download already in flight finishes into the staging dir. Any other client that sets the same context and then closes resets it too (last set wins, close resets), so a concurrent DevTools/Playwright client can undo or redirect the setting.
- `allow` with two downloads of the same URL writes one file (the later one wins, both report `completed`); `allowAndName` writes one file per guid. 157 reports the final `filePath` in `Browser.downloadProgress`; 118 does not.
- Attribution: `Page.downloadWillBegin` on the clicked tab's page socket covers the tab's own frame (links, POST forms, service-worker responses, blob downloads). Downloads started by a new window or a cross-site (out-of-process) iframe appear only as `Browser.downloadWillBegin` on the socket with `eventsEnabled`, with `frameId` = the new target or the iframe target; tying them to the clicked tab needs the browser socket's `Target.targetCreated` `openerId` (new window) or the iframe target's `parentFrameId`, which 157 lists and 118 does not.
- `post`, one-time, chunked and gzip downloads complete with one request and correct bytes under `allow`; under `deny` the request is still made (a one-time URL is consumed).

Not tested: other operating systems; a relative `downloadPath` with an actual download; Chrome's download bubble/shelf beyond its window title; a headed run of E3-E5; downloads started with no user click (timers, `navigator.serviceWorker` `clients.openWindow`); what the user's own Chrome profile setting does beyond `prompt_for_download` (for example a managed download-directory policy).
