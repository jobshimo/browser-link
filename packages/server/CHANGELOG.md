# Changelog

## [0.27.1](https://github.com/jobshimo/browser-link/compare/v0.27.0...v0.27.1) (2026-08-09)

### Bug Fixes

- **flow:** close the advisory findings from the two adversarial reviews of the detached-execution slices. None of them changed what 0.27.0 could do; every one of them made it report something slightly untrue, which for a feature whose entire justification is "an agent can find out what a flow with nobody attached actually did" is the failure mode that matters. (1) **cdp-direct kept an unbounded manifest.** The extension caps a stored manifest at `MAX_DETACHED_MANIFEST_BYTES` (128 KB) and says so out loud with `manifest_truncated: true`; the in-process cdp-direct registry kept whatever the runner handed back, so a 500-iteration `repeat` pinned an arbitrarily large array in server memory for up to ten records at a time, and the README's "same manifest" parity claim held only for small ones. The same ceiling now applies on both transports, `manifest_truncated` is part of the cdp-direct `flow_status` payload, and the summary event's `manifest_available` reports `false` when the manifest was dropped instead of unconditionally `true`. (2) **`stopped_by: 'grant-revoked'` was declared but unreachable.** `cdp/detached-flows.ts` has carried that stop reason since 0.27.0, but the transport combined the registry's stop check and the negated gate check with a boolean OR, so revoking the cdp-direct grant mid-run short-circuited past the registry and the flow reported a plain `'cancelled'` — indistinguishable from a `browser.flow_cancel`, which is exactly the distinction an agent needs to not retry into a gate that is still shut. The gate branch now cancels THROUGH the registry with its own reason. (3) **The byte cap measured the wrong unit.** `measureJsonBytes` used `JSON.stringify(value).length`, which counts UTF-16 code units while the `chrome.storage.session` quota counts bytes; a manifest of CJK or emoji page text is three to four bytes per code unit, so a record up to four times over the ceiling passed the check and was refused by the store the cap exists to keep it out of. It now encodes with `TextEncoder`. (4) **The pending-event flush could double-publish.** `eventPending` is only cleared by a write queued after the event goes out, so two fast reconnects of the same tab could both read the same still-pending record and send its `flow-finished` event twice; an audit trail that double-counts a flow is as wrong as one that drops it. A module-level in-flight set now holds a flow id from the send until the clearing write settles, and a write that failed leaves the flag set so the next flush legitimately retries. (5) **The minimal fallback record left one unbounded field.** `minimalDetachedFlowRecord` — the retry written when storage has already refused the full record — dropped the manifest but kept the flow's page-derived `error` string verbatim, and a `find: multiple-matches` over a large table quotes every candidate. It is now bounded at 1024 characters with a visible ellipsis, on that path only: the normal terminal record still keeps the failure message whole.

### Internal

- **flow:** pin the manually-synced detached-flow constants with a cross-file drift test. The 30-minute ceiling is written three times — `MAX_DETACHED_FLOW_TIMEOUT_MS` in `tools/browser-dispatch.ts` (the up-front budget check), `MAX_DETACHED_FLOW_MS` in the extension's `flow-registry.ts`, and again in `cdp/detached-flows.ts` (the runner's wall-clock deadline) — each with a comment saying it is kept in sync by hand, and nothing checking that it was. A ceiling that disagreed between the validator and the runner would reject flows it can in fact run, or run flows past the bound they were validated against, silently and only for runs long enough to notice. The new guard reads the three sources the way `cdp/drift.test.ts` already reads its verbatim-copy siblings and asserts the numbers agree, and does the same for the 128 KB manifest ceiling and the 10-record cap now that both exist on both transports.

### Documentation

- **flow:** four corrections to the 0.27.0 docs, all found by the same reviews. `DECISIONS.md` §13 contradicted itself: the pre-existing bullet said phase 6 lifts the throughput ceiling "by eliminating `MAX_FLOW_TIMEOUT_MS`", and the bullet immediately below it — added in 0.27.0 — says the cap is not eliminated but changes in nature. The first bullet now states what actually shipped (a synchronous flow still obeys the 60s cap; `detach: true` is a form of execution the rule does not apply to, bounded by its own budget and the 30-minute ceiling) with its historical reasoning intact. The README's cdp-direct parity table no longer overclaims "same manifest" — it now names the shared 128 KB ceiling and the `manifest_truncated` flag, true as of this release, and documents `stopped_by: "grant-revoked"` as what a revoked grant reports. The Recent-flows sentence describing a worker-terminated outcome was missing a relative pronoun and read as a fragment. And `pruneDetachedFlowRecords`' evidence-over-quota trade is now stated as a decision in both the function comment and the detached-flow persistence section: a refused launch write drops every already-finished record across ALL tabs, unread manifests included, because an unread manifest can be re-derived from the page while a missing launch record makes a killed service worker undetectable.

## [0.27.0](https://github.com/jobshimo/browser-link/compare/v0.26.0...v0.27.0) (2026-08-09)

### Features

- **bridge + extension:** detached execution, `browser.flow_status` / `browser.flow_cancel`, and the action manifest — the last slice of `docs/specs/flow-supervised-execution.md` (slice 5; ROADMAP item 11), and the one that finally breaks the circularity the whole program was written to break. `browser.flow({ steps, detach: true })` returns AT ONCE with `{ flow_id, detached: true, started_at, steps, expires_at }` and keeps running in the background with every guarantee intact: trusted CDP input, the occlusion guard, per-iteration records, fail-fast with a recovery snapshot, and the popup's Stop button. Work longer than 60 seconds no longer has to become a raw `evaluate` loop that has none of them. **`MAX_FLOW_TIMEOUT_MS` is not deleted — it changes meaning**, and `DECISIONS.md` §13 has been revisited to say so: it stops being a consequence of having no lifecycle and becomes a turn-economics rule about how long the bridge parks ONE tool call, exactly like `browser.wait_for_tab`'s and `browser.evaluate`'s ceilings. A synchronous flow still obeys it and is still rejected up front, because nothing cancels a flow just because the bridge stopped waiting for it, and a dropped response to a flow that is still executing is precisely how an agent retry duplicates irreversible actions. A detached flow parks nothing, so the rule does not apply to it; it is bounded instead by `MAX_DETACHED_FLOW_TIMEOUT_MS` (30 minutes), which is both the ceiling its statically computed worst-case budget is validated against up front AND the wall-clock deadline at which it self-cancels reporting `stopped_by: 'expired'` — a distinct outcome from `cancelled`, because "I ran out of time" and "a person stopped me" call for different responses. What was deliberately NOT relaxed: the truthful budget is still computed and `repeat.max_iterations` is still mandatory. "Unknowable" is exactly what the duration of a loop that keeps clicking with no agent attached must never be. The ceiling is enforced as a DEADLINE checked at the same three dispatch points as the cancel flag rather than as a timer — a timer would fire while the runner is mid-step and could not stop anything anyway, and a request-derived `setTimeout` duration is a resource-exhaustion finding waiting to happen. **At most one detached flow per tab**; a second is rejected NAMING the running `flow_id`, because an error that just says "busy" leaves the caller unable to inspect or stop what is blocking them. **The manifest fell out free, as the spec predicted**: `runFlow` already accumulated `results[]` via `compactActionResult`, so a detached flow simply retains them, addressable by `flow_id` — `browser.flow_status` returns the exact `results` array a foreground flow would have returned, per step and per iteration inside a `repeat`, which is how "which 956 things did you just delete?" becomes a question the bridge can finally answer. `runFlow` itself was not touched at all, so `cdp/drift.test.ts` held trivially: the runner still only knows `stopped_by: 'cancelled'`, and the registry entry is what promotes that to `expired` or `worker-terminated` on the way out. `flow_status(tab_id, flow_id)` returns `{ flow_id, tab_id, state, detached, started_at, ended_at?, steps, steps_completed, iterations_completed?, stopped_by?, error?, manifest? }` with `state` one of `running | completed | cancelled | failed | expired | unknown`. While a flow runs you get live progress and NO manifest — the runner is still holding the results, and promising one mid-run would promise a shorter truth than the real one. `unknown` is a state, not an error, for the same reason cancelling an unknown id is a no-op: the caller asked what an id is doing, and "nothing I know of" is a truthful answer. The `tab_id` only ROUTES the call (the registry is bridge-wide), so a finished flow whose own tab has since closed is still readable through any other connected tab. `flow_cancel` is the **first server-side sender of the `tool.cancel` frame** v0.26.0 left ready and unused: it sends that out-of-band frame — deliberately uncorrelated, since the cancelled flow answers through its own original `tool.request` — then reads the state back with a `flow_status` call and returns it with `cancel_requested: true`, so an agent sees `cancelling: true` during the up-to-one-step gap rather than a synchronous claim the function cannot make. Like `dialog_respond`, and more importantly than it, `flow_cancel` deliberately bypasses the claim guard: requiring tab ownership to STOP a runaway loop would mean the one agent that can see the problem is the one agent that cannot fix it. **MV3 service-worker termination is settled the conservative way.** A `detached-flow:<flow_id>` record lands in `chrome.storage.session` BEFORE the first step is dispatched — a flow that acted before it was recorded would be exactly the invisible run this slice exists to prevent — and on the next service-worker start any record still marked `running` is by definition orphaned, so it is rewritten `failed` / `stopped_by: 'worker-terminated'`, written to the popup's Recent flows, and has its summary event flushed on that tab's next registration. **It is never resumed.** A detached flow exists to do irreversible bulk work; resuming one whose real progress died with the worker would double-act on an unknowable prefix of it, and a flow that LOOKS `running` while nothing executes it is worse than either. Its partial manifest is genuinely unrecoverable (it lived in the runner's closure; the alternative — a per-step write — is hundreds of storage writes per run to keep a counter warm), so `manifest_truncated: true` says so rather than presenting an empty array as "nothing happened". No keep-alive was added: keeping the worker alive on purpose changes the problem from "it can die" to "it shouldn't die", and the guarantee that matters is that it never lies about its state. **Exactly one `flow-finished` bridge event per detached flow**, never one per iteration — `MAX_EVENTS = 200` means a single 200-iteration run emitting per-iteration events would silently evict every other entry, turning the thing meant to make bulk work auditable into the thing that destroys the audit trail; a test pins both halves of that reasoning. The event is a summary (counts, duration, outcome) and the manifest is addressed separately by id. `flow-finished` joins `EXTENSION_EVENT_KINDS` rather than staying server-owned like `flow-recorded`, because it asserts only what the extension itself just did rather than something that had to pass server-side validation and land in a database. **Full cdp-direct parity, with one documented asymmetry.** A new in-process `cdp/detached-flows.ts` gives that transport the same one-per-tab rule, the same 30-minute `expired` ceiling, the same status payload keys and the same single summary event (added straight to `BridgeEventLog` through a sink installed at startup, since there is no extension to push a frame). It is deliberately NOT a verbatim copy under the drift guard: most of the extension's version is persistence for surviving worker termination, and there is nothing to survive here — if the browser-link process dies the flow dies with it and no state is left to be wrong about. The flip side, documented: detached state there is per-process, where the extension's survives in `chrome.storage.session` for the browser session. The popup Stop button has no cdp-direct equivalent either; `browser-link cdp revoke` remains the lever and now stops a detached flow within one step exactly as it stops a foreground one. **The popup surfaces detached flows as the thing that needs watching**: a running detached row is labelled `detached ·` and carries an amber dot instead of the connected green, and Recent flows gains the `expired` outcome plus a plain-language reason line for a worker termination. Recent-flow entries keep the counts-and-outcomes-only privacy contract untouched; the manifest — which does hold resolved selectors and step results, because that is what makes it useful — is never rendered there, is only ever returned over the bridge to an agent that can already read the page, is capped at 128 KB per record and 10 records, and dies with the browser session. **Known UX item, decided and disclosed:** a `dry_run` is now validated against the DETACHED ceiling regardless of whether `detach` was passed, and reports `budget_ms` and `requires_detach`. Before this, an oversized flow was rejected BEFORE it was projected, which made the one question `dry_run` exists to answer — "I am about to do this N times; would it even start?" — unanswerable for exactly the runs where it matters most. A dry run dispatches nothing, so there is no run to be too long. The over-60s rejection message for a real run now names `detach: true` as the first remedy instead of only suggesting the caller split a flow they could have detached. The agent-instructions block gains a `WORK LONGER THAN 60s` section teaching the whole lifecycle in order (dry_run → detach → poll `flow_status` → `flow_cancel`), the four states an agent must not misread, a "poll at a human pace" warning, and an explicit "do not detach work that fits in 60s"; `evaluate` is demoted one rung further, now the escape hatch for what `flow` + `repeat` + `detach` together cannot express. **One behaviour to know about `detach`:** the launch record's write is verified rather than fire-and-forget — on a storage rejection old manifests are pruned and it is retried once, and if it still will not land the flow is unregistered and the call returns an error naming the persistence failure, because a detached run with no record would act irreversibly with no evidence and answer `flow_status` as `unknown` instead of the documented `failed` / `worker-terminated`. 97 new tests (extension 370 → 409, server 1124 → 1182), including an unmocked timing test that drives the REAL `performWaitFor` poll loop over a live fake CDP target and proves a 20-second wait cut short mid-poll returns within one poll interval as `cancelled` rather than at its own deadline.

### Internal

- **three review follow-ups, folded in with the slice they belong to.** (1) `flow-registry.ts`'s `register()` JSDoc claimed it "returns the live entry so the caller can hand `shouldCancel` / `onProgress` closures straight over it" while the method returned `void`. Fixed by making the doc true rather than by deleting it: the detach wiring genuinely wants the entry (to stamp the late-arriving tab title, to close the progress sink over it, to read its deadline) and was otherwise going to do a second map lookup per step. (2) The per-tick `shouldCancel` check inside the REAL `performWaitFor` poll loops was only ever covered through mocked wait deps, so the advertised "worst case one step" bound for a step that can park for 30 seconds rested on a test that never ran the loop. There is now an unmocked timing test on the server transport: a 20-second `wait_for` against a live fake CDP target, the cancel flag flipped from inside the target's own command handler on the third poll, asserting the flow returns in well under a second with `stopped_by: 'cancelled'` (not a fabricated `timeout`) and that polling actually stops — plus a control case proving an uncancelled wait still runs to its own timeout, so the test measures the flag and not some unrelated early exit. (3) `chrome.tabs.onRemoved`'s `chrome.storage.session.remove` of the tab's flow-history key ran OUTSIDE the serialized `flowHistoryWrites` chain, so a still-running flow's late append could resurrect a key that had just been dropped — and Chrome reuses tab ids within a session, so that stale key eventually shows one tab's flows under another's. Fixed with both halves the review suggested, because either alone leaves a hole: the delete now goes through the same chain (which orders it against every write already queued), and a `flowHistoryDroppedAt` timestamp makes `recordFinishedFlow` skip the append for a flow that started before its tab was removed (which handles the late write queued AFTER the delete — `cleanup` only ASKS a tab's flows to stop). The map is cleared when a tab connects under the same id, so it never grows past live-plus-recently-closed tabs.

## [0.26.0](https://github.com/jobshimo/browser-link/compare/v0.25.2...v0.26.0) (2026-08-09)

### Features

- **bridge + extension:** flows can now be STOPPED — flow identity, real cancellation, and the popup Flows panel that invokes it (slices 4 and 6 of `docs/specs/flow-supervised-execution.md`; ROADMAP items 9 and 10). Shipped as ONE release on purpose: cancellation alone would have been dead code, because a synchronous `browser.flow` blocks the very agent that would have to cancel it, so the popup's Stop button is the first — and today the only — thing that can pull the lever. What made it affordable is that `runFlow` was already a pure orchestrator over an injected `FlowDeps`, and that v0.25.0's refactor left a single `executeLeafStep` driving both the top-level sequence and the repeat body: cancellation is `deps.shouldCancel?.()` checked at three dispatch points — before every top-level step, before every `repeat` iteration, and before every step INSIDE a repeat body — plus the same flag threaded into `performWaitFor`'s poll loop on both transports, which is what keeps the advertised "worst case one step" honest for a step that can legitimately park for 30 seconds. Everything else is plumbing: no `AbortController`, no signal, no loop surgery. **A cancelled flow is a SUCCESS, not an error** — `{ ok: true, stopped_by: 'cancelled', steps_completed: N, results: [...] }` — because the steps that ran really ran, and after a bulk run stopped half-way "what did it already do?" is the only question that matters; an error payload could not answer it. A `repeat` cut short reports its own `stopped_by: 'cancelled'` with the `iterations_completed` it finished, and when the stop lands part-way through an iteration those inner results are reported as a separate `partial_iteration` rather than either being discarded or being miscounted as a completed iteration. A `wait_for` stopped mid-poll returns `reason: 'cancelled'` rather than `'timeout'`, which the step executor turns into a clean cancellation instead of a fabricated timeout failure with a recovery snapshot — and a `while_found` probe cut short the same way reports `cancelled` instead of falsely claiming the list drained. Every `browser.flow` call is now assigned an opaque server-minted `flow_id` (`randomUUID`, unguessable because the id IS the capability to stop something), forwarded to the transport in the request params and stamped onto the result — success, fail-fast failure and cancellation alike, since the failure payload is exactly when an agent wants to know which run it is looking at. The extension keeps an in-flight registry (`Map<flow_id, { tabId, startedAt, steps, cancelled, progress }>`) in service-worker memory by design: if Chrome terminates the worker the flow dies with it and the panel shows nothing running, which is the truth, whereas a registry that survived would describe flows that no longer exist. Cancelling an unknown or already-finished `flow_id` is a deliberate no-op, never an error — the popup, the agent and the flow's own completion race by nature, and every one of those races ends with the flow not running. A new `ToolCancelMessage { kind: 'tool.cancel', flow_id }` joins `ServerToExtension` (both wire-type copies) and is handled by the extension today, so the later `browser.flow_cancel` tool needs no protocol change; it is deliberately uncorrelated to a `tool.request` id, because the cancelled flow answers through its own original response. **The popup gains a Flows panel**: Running lists every in-flight flow across EVERY connected tab (a runaway flow is rarely on the tab you are looking at) with tab title, elapsed time, live progress — `step 3/7`, or `step 2/5 · iteration 12/50` inside a repeat, fed by a new `deps.onProgress` reported BEFORE each dispatch so the panel shows what is running rather than what last finished — and a one-click Stop with no confirmation, showing `Stopping…` for the one step it takes to land. Recent lists the last 20 finished flows of the current tab from `chrome.storage.session`, which dies with the browser session by design: this is an operator view, not an audit log (the durable manifest belongs to the detached-execution slice). History entries carry UI structure and outcomes ONLY — counts, durations, a step index, a step KIND — and the failure MESSAGE is dropped rather than trimmed, because a real `find` failure quotes the page back at you (candidate labels, names, order numbers); the same rule the persistent map already lives under, here enforced by a single `toHistoryEntry` that names every field instead of spreading, and pinned by tests that assert page text cannot reach a stored entry. Running rows are updated in place rather than re-rendered, because swapping a row out between mousedown and mouseup silently eats the click, and a kill switch that loses a press is not a kill switch. The whole panel stays hidden when nothing is running and nothing is remembered, so an idle popup looks exactly as before. **cdp-direct gets the same primitive and a real lever for it**: there is no extension and therefore no popup there, so `browser-link cdp revoke` IS the kill switch — and it now works, with the in-process runner re-checking the grant before every step. Until this release a mid-flow revoke was grandfathered until the flow finished (bounded by the 60s budget, but not stoppable); the README's caveat saying so has been replaced with the new behavior. Both drift-guarded `flow.ts` copies carry the change byte-identically. `browser.flow`'s own tool contract now teaches the outcome an agent has never seen before, with the instruction that matters most attached to it: a cancelled flow is a person deciding to stop you, so report what completed and ASK — never relaunch it, because retrying it would repeat the irreversible actions they just interrupted. One honest edge, documented everywhere it matters: a `sleep` step and a repeat's `delay_ms` are each one step and each run to completion (up to 30 s) before the next check. 59 new tests (extension 323 → 370, server 1112 → 1124), including a transport-level test that revokes the grant from inside the fake CDP target's own command handler and proves the remaining steps dispatch nothing.

### Internal

- **tooling:** `eslint.config.mjs` now ignores `.taskboard/**` and pins `tsconfigRootDir` in the TEST-file block. An agent worktree under `.taskboard/` is a full second checkout, tsconfig files and all, which made typescript-eslint see several candidate project roots and refuse to parse ANY file — `pnpm run lint` failed with 513 parse errors ("multiple candidate TSConfigRootDirs are present") whenever one happened to exist, on a repo with zero actual lint violations. Ignoring the scratch copies fixes the immediate case; pinning the root turns the parser's inference into a stated fact, so the next stray nested checkout (a vendored copy, a second worktree) cannot resurrect the same failure. The type-aware source block already pinned the same value.

## [0.25.2](https://github.com/jobshimo/browser-link/compare/v0.25.1...v0.25.2) (2026-08-09)

### Documentation

- **CORRECTION to the 0.25.0 release notes and docs:** `repeat`'s advertised throughput was wrong by roughly 4x, and the correction changes how the feature should be described. 0.25.0 claimed "hundreds of iterations in ONE round trip" and the spec/ROADMAP/DECISIONS put a number on it — "~200 iterations per call", with the field report's 956-deletion task dropping "from ~25 round trips to ~5". That arithmetic silently assumed a click step costs about what its `delay_ms` costs. It does not: in the flow budget model a click is charged its settle ceiling, 2500ms with default settle or 500ms with `settle_ms: 0`, and a `while_found` condition adds a 500ms probe per iteration on top of the delay. Exercising the shipped build against a live page rather than re-reading the code produced the real ceilings, now measured and locked by tests: with the budget being `2000 + max_iterations × (inner steps + delay_ms + a 500ms while_found probe) ≤ 60000`, one click with default settle fits **23** iterations, with `settle_ms: 0` fits **116**, and the realistic throttled drain loop — one click, `settle_ms: 0`, `while_found`, `delay_ms: 250` — fits **46** (verified live: 46 accepted, 47 rejected at 61s). Draining a 956-row list is therefore ~21 calls, not ~5. The honest framing, now used everywhere: `repeat` is **not** primarily a throughput win over an `evaluate` loop — it is a SAFETY win (trusted CDP input, the occlusion guard, a per-iteration record, and a flow that is bounded and rejectable before it starts), and the throughput ceiling is precisely what removing `MAX_FLOW_TIMEOUT_MS` in a later slice lifts. Corrected in `README.md` (which now carries the budget formula and a measured per-configuration table), `docs/specs/flow-supervised-execution.md`, `ROADMAP.md`, `DECISIONS.md` §13 and the agent-instructions `BULK WORK` section — the last of which now also tells agents to set `settle_ms: 0` on the inner click, since leaving it at the default silently halves the ceiling to 23. Three new boundary tests assert each documented number and its off-by-one rejection, so a published figure cannot drift from the code again. The 0.25.0 entry below is left as written: it is the historical record of what that release actually claimed.

## [0.25.1](https://github.com/jobshimo/browser-link/compare/v0.25.0...v0.25.1) (2026-08-09)

### Bug Fixes

- **cli:** the in-app self-update (`[u] Check for updates` → install, and `browser-link update`) never worked on Windows and could crash the TUI instead of reporting a failure. Three defects, found by reproducing the real spawn rather than reading the code. (1) **`spawn EINVAL`.** `npm` on Windows is `npm.cmd`, and since Node 18.20.2 / 20.12.2 / 21.7.3 — the CVE-2024-27980 mitigation — spawning a `.cmd` or `.bat` WITHOUT a shell is refused outright. The previous fix had correctly switched the binary name to `npm.cmd` but deliberately avoided `shell: true` to dodge an argument-quoting surface, which turned an ENOENT into an EINVAL: necessary, but not sufficient. (2) **The never-throws contract was broken.** That EINVAL throws SYNCHRONOUSLY out of `spawn`, so it never reaches the `child.on('error')` handler; it escaped the promise executor and rejected out of `runSelfUpdate`, whose own doc comment promises it "always resolves … never throws so the UI doesn't have to wrap calls in try/catch" — and the UI indeed has no try/catch, so the user got a crash rather than a clean "✗ Update failed". (3) **A platform-dependent test** pinned only the npm binary and not the shell decision, so it passed on CI's Ubuntu and would have failed on a Windows dev machine. The fix removes the problem class instead of patching around it: the install now runs npm's own CLI entrypoint with the Node binary already executing (`node <prefix>/node_modules/npm/bin/npm-cli.js install -g <pkg>@<target>`), resolved next to `process.execPath`. That is shell-free on **every** platform — no `.cmd` shim so no EINVAL on Windows, no concatenated command line so no Node `DEP0190` deprecation warning printed at the user mid-update, and one identical code path on macOS, Linux and Windows. Layouts where npm is not laid out that way (shim-based managers such as Volta) fall back to the platform shim, with `shell: true` on Windows because it is mandatory there. Because that fallback does reach cmd.exe's parser, both halves of the package ref are now allow-list validated BEFORE anything is spawned: the target must be `latest` or an exact semver (a shell metacharacter, command substitution, path traversal or version range is refused without spawning anything), and the package name must match npm's own name grammar via the `assertSafeNpmName` gate already used for the registry lookup. Finally, a global-install permission failure — the most common way this fails on macOS and Linux, where npm's own last line is just `EACCES: permission denied` — now appends the two real remedies (run with elevated permissions, or point npm at a user-owned prefix) instead of leaving the user to search for them. 17 new tests covering the synchronous-throw path, every refused and accepted target shape, the refused package name, the permission hint firing only on permission failures, the shell-free preferred path on all three platforms, and both shim fallbacks.

## [0.25.0](https://github.com/jobshimo/browser-link/compare/v0.24.0...v0.25.0) (2026-08-09)

### Features

- **bridge:** `browser.flow` gains a bounded `repeat` step and a `dry_run` projection mode — the slice that actually closes the bulk-work gap (slice 3 of `docs/specs/flow-supervised-execution.md`; ROADMAP item 8). `flow` could not express repetition at all, so the sanctioned path for "click every element matching X, pause, repeat until the list drains" was a loop inside `browser.evaluate` — precisely where every guarantee the bridge exists to provide is lost: `el.click()` is `isTrusted:false`, nothing hit-tests for occlusion, there is no recovery snapshot and no record of what happened. `{ repeat: { steps, max_iterations, while_found?, delay_ms? } }` runs hundreds of iterations in ONE round trip with all of it intact. It is bounded BY CONSTRUCTION, which is what makes it safe to ship before cancellation exists: `max_iterations` is REQUIRED, so the worst case stays statically computable and the existing up-front `MAX_FLOW_TIMEOUT_MS` rejection still bounds every flow (the budget is `max_iterations × (inner steps + delay_ms + a while_found probe)`, with the once-per-flow base overhead correctly charged once rather than per iteration); repeats do NOT nest; and inner steps count against the same 20-step ceiling as outer ones, since a ceiling that counted only the outer array would let one repeat smuggle in an arbitrarily long body. Each iteration starts with a FRESH implicit target and none escapes in either direction — a `find` inside the body cannot feed a click after the repeat, and one before it cannot feed a click inside. `while_found` makes the stop condition declarative: before each iteration the loop checks whether that selector still matches something VISIBLE and stops the first time it does not (`stopped_by: "condition"` vs `"max_iterations"`), which retires the field report's "paginated counters lie" observation at the root — no counter parsing, no hand-rolled stall detector, no phantom last item when the counter vanishes at zero. Known and deliberate limit, documented in both the tool gotchas and the README: `dry_run` answers "would this start, and what is my ceiling", NOT "how many elements match" — a live match count would require a new deep-query primitive and is a follow-up. Internally `runFlow` was refactored so a single `executeLeafStep` drives both the top-level sequence and the repeat body (one implementation, never two that can drift), verified by the entire pre-existing 1379-test suite passing unchanged before a single new test was added. Both drift-guarded `flow.ts` copies carry the change identically, `repeat` and `dry_run` work the same on extension and cdp-direct transports, and `browser.map.save` recipes inherit the grammar through the shared validator. - **bridge:** `browser.flow` gains a `sleep` step — `{ sleep: { ms } }`, 1..30000 — closing the one gap in the flow grammar that had no workaround inside the guaranteed zone (slice 2 of `docs/specs/flow-supervised-execution.md`; ROADMAP item 7). Flow had six step kinds and no fixed pause, and `settle_ms` structurally cannot serve as one: it is a quiet-PERIOD wait that returns as soon as the page stops mutating, so on an already-idle page it collapses to nothing and can never throttle anything. ### Security

### Features

- **bridge:** `browser.find` returns actionable near-miss suggestions instead of a bare failure. On `reason: "not-found"`, the response now carries `near_misses`: up to 3 VISIBLE candidates (`{ text, selector, role? }`) ranked by (1) case-insensitive substring containment of the query in the candidate's accessible text/name, then (2) token overlap — the same deep walk + visibility gate the primary match scan already uses, so a near-miss selector is exactly as trustworthy as a normal `find` hit. Omitted entirely when nothing scores, so a genuinely empty page still returns the same lean `{ matched: false, reason: "not-found" }` as before — no junk suggestions padding the response. When `role` narrowed the scan and the text DOES exist on an element of a different role, `error` now names the exclusion explicitly (e.g. `text matched 2 elements but none with role "button" — closest: <div onclick> "GIF picker"`), reusing the `near_misses` shape for the "closest" candidates instead of a bare miss that would have cost the agent a diagnostic round trip re-running `find` without `role`.
- **bridge:** `browser.click` and `browser.type` distinguish an invalid CSS selector from a well-formed selector that matches nothing. Previously both cases silently collapsed into the same "Element not found" error — a typo'd selector (`"button["`) looked identical to a stale one. The in-page resolver now pre-checks `document.querySelector(selector)` before the deep search runs; a `SyntaxError` there returns `Invalid selector "…": <browser's own message>` instead of the misleading not-found error. `browser.press`'s optional `selector` and `browser.find` are unchanged in v1 — this is scoped to the two tools where a malformed selector is most commonly hand-typed against a snapshot result.
- **bridge:** new `browser.state` read tool — a compact orientation snapshot for when an agent only needs to know where it is, not the full interactive element list a `browser.snapshot` returns. Returns `{ url, title, viewport:{w,h}, focused?, dialogs?, scroll? }`. `focused` descends `document.activeElement` past shadow-root and same-origin-iframe boundaries (`shadowRoot.activeElement`, then `contentDocument.activeElement`) to the actual innermost focused element — `document.activeElement` alone only ever reports the shadow host or the `<iframe>` element itself — and carries `{ selector, tag, ambiguous? }` through the same `genSelectorInfo` uniqueness check `snapshot`/`find` use. `dialogs` lists visible `[role=dialog]`, `[role=alertdialog]` and open `<dialog>` elements as `{ selector, role, label? }`, with `label` best-effort from `aria-label` / `aria-labelledby` / the first heading inside. Every optional field — `focused`, `dialogs`, `scroll` — is omitted when there is nothing to report (focus at `<body>`, no open dialog, scroll at its default `(0,0)`), keeping the common case a handful of fields. Read tool: no tab claim, included in the `readonly` permission preset, same bucket as `browser.snapshot`/`browser.find`.
- **map:** `browser.map.save` / `browser.map.recall` gain named, replayable flow recipes — connecting the persistent UI map to `browser.flow` (v0.17.0). `browser.map.save` accepts an optional `flows: [{ name, description?, steps }]`; `steps` must follow the EXACT `browser.flow` step grammar and is validated with the SAME rules `browser.flow` itself enforces (see Internal) — a steps array the flow tool would reject is rejected here too, before anything (including the base entry) is written. Saving an existing `name` for the same app upserts it. `browser.map.recall` returns the app's saved flows (`name`, `description`, `steps`, `use_count`) alongside the existing selector/gotcha entries, not filtered by `url` — a flow recipe is not tied to a single route the way a selector usually is. The intended pattern, taught in the tool docs and the agent-instructions block: recall → ADAPT the steps (substitute placeholder text like `type text "<QUERY>"` for the real value the user asked for) → `browser.flow` with the adapted steps. This reinforces, not relaxes, the existing map privacy rule: flows store UI STRUCTURE only, never domain data (real names, IDs, dates, message content) — placeholders exist precisely so a flow can be saved without ever writing that data to disk. `browser.map.record_use` is deliberately NOT extended to flows: its `ok:true/false` verified/failed contract does not map cleanly onto a `use_count`-only tracking model with no failure state — re-`browser.map.save`ing a recipe is the refresh path instead.

## [0.17.0](https://github.com/jobshimo/browser-link/compare/v0.16.0...v0.17.0) (2026-07-11)

### Features

- **bridge:** new `browser.flow` tool — runs a declarative sequence of `find`/`click`/`type`/`press`/`wait_for` steps in ONE round trip instead of one MCP call per step. A common UI task (locate a target, click it, wait for a result, fill it in, submit) used to cost an agent 5-10+ sequential MCP round trips — each one a full LLM inference — before it could report back. With `browser.flow`, the same task is one call (two if a step fails and a corrective follow-up is needed). Steps run strictly in order and fail fast: the first failing step stops the flow immediately, there is no branching. A `find` step's resolved selector becomes the IMPLICIT TARGET for the very next `click`/`type`/`press` step that omits its own `selector` — an explicit `selector` on that step always overrides it and leaves the implicit target untouched for a later step to consume. `type` and `press` steps that end up with no selector at all (no explicit one, no implicit one) act on whatever currently has focus, exactly like standalone `browser.press`; only `click` truly requires a resolved target, since there is no "click whatever has focus" concept. `click`/`type`/`press` steps default `settle_ms` to 150, same as the standalone tools. Example (GIF picker): `{find:{text:"GIF",role:"button"}}, {click:{}}, {wait_for:{selector:"[data-testid=gif-search]",condition:"visible"}}, {type:{selector:"[data-testid=gif-search]",text:"shrek"}}, {press:{key:"Enter"}}` — 5 steps, 1 round trip. On success returns `{ ok: true, steps_completed, results }` with a compact per-step result (`{selector}` for `find`, `{ok, settle?}` for everything else). On failure returns `{ ok: false, failed_step, step_kind, error, steps_completed, recovery_snapshot }` — `error` is the same message the standalone tool would have returned for that failure, and `recovery_snapshot` is a focused `browser.snapshot({only_interactive:true, max_interactive:40})` of the page as it stands, so the agent sees where the flow stopped without a follow-up round trip. `evaluate` and `navigate` are deliberately NOT flow steps in v1 — arbitrary JS inside a flow raises permission-model questions this tool does not solve yet, and a mid-flow navigation can tear down the very document later steps expect to act on. Action tool: participates in the tab-claim layer exactly like `browser.click`/`browser.type`/`browser.press`.

## [0.16.0](https://github.com/jobshimo/browser-link/compare/v0.15.0...v0.16.0) (2026-07-11)

### Features

- **bridge:** new `browser.press` tool — dispatches a single trusted key press (optionally with modifiers) via CDP `Input.dispatchKeyEvent`, producing real `isTrusted: true` keyboard events. Until now, the only way to send Enter/Escape/Tab/arrow keys was a synthetic `KeyboardEvent` through `browser.evaluate` — this repo's own v0.14.0 CHANGELOG already documents, empirically, that Qt-WASM discards synthetic input, and the same is true of many rich text editors and autocomplete widgets that check `event.isTrusted` before acting. `key` accepts a human name (`Enter`, `Escape`, `Tab`, `Backspace`, `Delete`, `ArrowUp`/`ArrowDown`/`ArrowLeft`/`ArrowRight`, `Home`, `End`, `PageUp`, `PageDown`, `Space` — case-insensitive) or a single printable character (case-sensitive, `"a"` vs `"A"`, plus common punctuation and shifted digit-row symbols). `modifiers` is an array of `Alt`/`Control`/`Meta`/`Shift`, encoded as the CDP bitmask, for shortcuts like Ctrl+A or Cmd+S. An optional `selector` focuses an element first through the same deep Shadow DOM / iframe search `click`/`type`/`find` already use; omitted, the key goes to whatever currently has focus. Implementation dispatches a `keyDown`-or-`rawKeyDown` / `char` / `keyUp` sequence — `rawKeyDown` only when the key produces no text (control/navigation keys), keeping the `char` event as the single source of actual text insertion so nothing double-types. `Enter` carries text `\r` (matching Puppeteer's `USKeyboardLayout`), so its `char` event produces the KEYPRESS whose default action drives the WHATWG implicit form submission — pressing Enter in a form field actually submits the form. Shift is auto-added for characters that require it on a US layout (uppercase letters, shifted punctuation like `@`), so `key:"A"` types an uppercase A without an explicit modifier. - **bridge:** `browser.click`, `browser.type` and `browser.press` accept an optional `settle_ms` (default 150, max 2000; `0` disables) and `settle_timeout_ms` (default 2000, max 10000). After dispatching, the extension installs one `MutationObserver` on `document` (subtree, childList, attributes, characterData) and waits until no mutation lands for `settle_ms` consecutive milliseconds, capped at `settle_timeout_ms`. The result gains a compact `settle` object — `{ settled, duration_ms, mutation_count, url_changed?, focus_moved? }` — with `url_changed`/`focus_moved` present only when they actually changed during the wait. This folds the wait_for + snapshot round trip most flows need after an action directly into the action call: a click that triggers an async re-render no longer needs a separate `browser.wait_for` just to know the page settled. The occlusion guard on `browser.click` is untouched — settle only runs after a successful dispatch. The settle wait is failure-isolated from the action: when the action itself triggers a full-document navigation, the execution context the settle expression runs in is destroyed mid-wait — the action result stays `ok:true` (it DID land) and `settle` degrades to `{ settled: false, reason: "context-destroyed" }` instead of the whole call flipping to an error that would bait a duplicate retry. Honest limitation, documented on the tools: settle proves QUIET, not EFFECT — mutations completing before the observer installs (right after dispatch) and async reactions starting after the quiet window are both invisible, so `mutation_count: 0` with `settled: true` does not prove the action had no effect; `browser.wait_for` remains the tool for a specific expected condition.

## [0.15.0](https://github.com/jobshimo/browser-link/compare/v0.14.1...v0.15.0) (2026-07-11)

### Features

- **bridge:** `browser.snapshot`, `browser.find`, `browser.click` and `browser.type` now pierce OPEN Shadow DOM roots and same-origin iframes, nested arbitrarily (shadow roots inside iframes and vice versa). Previously all four walked the DOM with plain `document.querySelector` / `querySelectorAll`, so anything behind an `attachShadow({ mode: "open" })` boundary or inside an in-page iframe was invisible to agents. The scan enumerates every reachable root and queries each independently; selectors returned by `snapshot`/`find` are verified unique across the FULL deep search scope before being handed out, so the find → click round trip keeps working when the target lives inside a web component or iframe. Entries for iframe-hosted elements carry an optional `frame` field (the CSS selector of the innermost hosting iframe) — the result shape stays backward compatible.
- **bridge:** `browser.click` gains an occlusion guard. Before dispatching CDP mouse events, the click point is hit-tested starting from the target's own root (shadow root or iframe document, descending nested open shadow roots). If a different element covers the point — modal backdrop, loading overlay, dropdown — the call returns `ok:false` with `Element covered by <tag#id.class> — click the covering element or dismiss it first` instead of silently clicking the wrong thing. Clicks on the target itself, its own descendants, or a wrapper containing it (composed-tree containment) pass. A new optional `force: true` parameter skips the guard as a documented escape hatch. `pointer-events: none` overlays never block (elementFromPoint skips them natively).
- **bridge:** correct coordinate mapping for iframe-hosted elements. CDP `Input.dispatchMouseEvent` takes TOP-LEVEL viewport coordinates; clicks and `find` coords now accumulate each ancestor iframe's bounding rect PLUS its border and padding (the embedded document's viewport origin sits at the frame's content box, not its border box). Every ancestor iframe is scrolled into view alongside the target before measuring.
- **bridge:** click point accuracy for line-wrapped inline elements. The center of `getBoundingClientRect()` for a link wrapped across two lines can land in the unpainted gap between line boxes — hit-testing there reported a false blocker and dispatching there missed. Both the occlusion hit-test and the dispatched CDP coordinates now use the center of the FIRST client rect (`getClientRects()[0]`), which is always a painted fragment; they are guaranteed to be the same point.

### Known limitations

- CLOSED shadow roots (`attachShadow({ mode: "closed" })`) are unreachable from page-world JS — `element.shadowRoot` is `null` by design and there is no CDP-level workaround via `Runtime.evaluate`.
- Cross-origin iframes are unreachable under the same-origin policy; their content is invisible to the scan (access is caught, never thrown).
- Two structurally-identical component twins in different roots (byte-identical shadow internals, no id/testid/label) cannot be told apart by any CSS selector — no syntax scopes a selector to one root. Affected `snapshot`/`find` entries carry `ambiguous: true`: the selector resolves first-match-wins in a deterministic traversal order, must be used immediately, and must never be saved to the persistent map.
- `browser.drag` does NOT yet resolve its endpoint selectors through the deep search — deferred to a later release. **Resolved in v0.20.0** — see that release's notes below.

## [0.14.0](https://github.com/jobshimo/browser-link/compare/v0.13.4...v0.14.0) (2026-05-20)

### Features

- **bridge:** new `browser.canvas_screenshot` tool. Captures a `<canvas>` element from the connected tab as PNG/JPEG and returns it base64-encoded. Designed for pages whose visible UI is rendered to a canvas — Qt for WebAssembly (Victron VRM Remote Console, Venus OS, Felgo apps), WebGL games, custom rendering engines — where `browser.snapshot` and `browser.find` return nothing useful because there is no DOM inside the canvas to inspect. ### Rationale

Acting on a canvas page is intentionally NOT exposed yet. The only path to real input is `chrome.debugger.sendCommand('Input.dispatchMouseEvent', ...)`, which generates events with `isTrusted: true` from Chromium's input pipeline. Implementing that needs careful design around per-tool permissions and the existing claim layer; it will land in a future release. The screenshot tool delivers the immediate value (the LLM can SEE the page) without dragging the security review of the input path along with it.

## [0.12.0](https://github.com/jobshimo/browser-link/compare/v0.11.0...v0.12.0) (2026-05-18)

### Features

- **bridge:** popup-aware bridge — three new MCP tools so agents can survive (and use) the things that block tabs.
  - `browser.dialog_respond({ tab_id, accept, prompt_text? })` — respond to a native `alert` / `confirm` / `prompt` / `beforeunload` dialog. browser-link does NOT auto-dismiss anymore: when CDP reports `Page.javascriptDialogOpening`, the extension emits a `dialog-opening` event in `browser.events` (`{ tab_id, type, message, default_prompt }`) and leaves the dialog open. The agent reads it, decides, and answers. Bypasses the claim guard so any agent observing can unfreeze a tab. The popup also exposes Accept / Cancel buttons as a manual escape hatch for when no agent has this tool in its preset.
  - `browser.wait_for_tab({ opened_from, url_substring?, timeout_ms? })` — block until a new tab spawned by a previous action on a connected tab appears in the bridge stream. The extension auto-connects any tab whose `openerTabId` is already connected (via the same `Connect` flow the popup uses), then emits `tab-created` with `opened_from = the opener's server tab id`. `wait_for_tab` polls the stream and, on match, **auto-claims** the new tab under the calling agent — the wait IS the explicit intent. Returns `{ matched, tab_id?, url?, elapsed_ms, checks, claimed?, claim_conflict?, reason? }`.
  - `browser.set_permission({ tab_id, origin, name, state })` — pre-set a browser permission (geolocation, notifications, camera, microphone, clipboardReadWrite, clipboardSanitizedWrite, sensors) so the page API responds silently and no native prompt surfaces. Backed by `chrome.contentSettings` (not CDP `Browser.setPermission`, which would need a browser-level target unreachable from `chrome.debugger` in MV3 — see Internal notes). Scoped per-ORIGIN as a `<origin>/*` URL pattern. States map as granted→allow, denied→block, prompt→ask.

- **extension popup:** version-mismatch banner. The MCP server now stamps its `VERSION` into the `tab.registered` payload; the extension stores it on `TabState` and the popup compares it against `chrome.runtime.getManifest().version` (re-checked every 800 ms while the popup is open). When they drift the popup surfaces a red banner — _Extension X · Server Y — Reload the extension so both halves run the same code_ — plus a one-click `Open chrome://extensions` button that lands the user on the extension's own card, ready to hit the circular refresh icon. Hidden when aligned, or when no tab has registered yet. **Why it matters at this version**: 0.12.0 widens the wire protocol (new `bridge.event` message), so an extension that lags behind misses dialogs / tab-created events silently. The banner makes that visible the moment the user opens the popup.
- **catalogue:** five tools that were already wired up (`browser.claim_tab`, `browser.release_tab`, `browser.my_tabs`, `browser.events`, `browser.reset`) are now in `TOOL_CATALOGUE` so `browser-link tools disable <name>` / `enable <name>` / the Permissions menu can toggle them like the others. Previously these were always-on even when a user wanted to lock the agent out — particularly relevant for `browser.reset`, which is destructive. Catalogue is now exactly 26 tools.

### Internal

- New `bridge.event` message in the wire protocol (`ExtensionToServer` union) so the extension can push out-of-band events to the server's `BridgeEventLog`. Closed allowlist on the server side — only `dialog-opening`, `dialog-closed`, `tab-created` are accepted from the renderer; lifecycle events (`primary-elected`, `tab-registered`, etc.) stay server-owned and cannot be spoofed.
- `BridgeEventLog` is now push-based as well as pull-based. New `subscribe(fn, { replayWithinMs })` registers a listener that fires synchronously inside `add()`. Optional `replayWithinMs` replays recent events to the listener before subscribe returns — solves the race where the agent fires the action and `wait_for_tab` in the same tool batch and the source event lands in the buffer milliseconds before `wait_for_tab` registers.
- `browser.wait_for_tab` is push-based now. No polling loop, no `sinceId` snapshot. Registers a listener via `subscribeEvents` with `replayWithinMs: 1500`, resolves immediately when a matching `tab-created` lands (or comes through the replay) — `elapsed_ms: 0` is the common case.
- Auto-connect for spawned tabs: `chrome.tabs.onCreated` watches for tabs whose `openerTabId` belongs to an already-connected tab. Polls `chrome.tabs.get` up to 5 s for the new tab's `url` to surface (Chrome reports an empty `url` at the moment of `onCreated`; `connectTab` short-circuits on empty url, hence the poll), then runs the same `connectTab` flow as the popup button — debugger attach, `Page` + `Runtime` + `Log` + `Network` + `DOM` enable, WS register. Then the `tab-created` event lands on the bridge stream.
- `Page.javascriptDialogOpening` / `Page.javascriptDialogClosed` listeners in the extension's debugger handler — both emit `bridge.event` and keep a `pendingDialog` field on `TabState` for the popup to surface.
- `browser.set_permission` is backed by `chrome.contentSettings`, NOT CDP `Browser.setPermission`. Reason: `Browser.*` is a browser-level CDP domain and `chrome.debugger.attach({ tabId })` only exposes the tab-level target — the MV3 chrome.debugger API does not expose the flat-protocol `sessionId` mechanism that would let us escalate to the browser target. `chrome.contentSettings` is the surface that IS reachable, at the cost of supporting fewer permission names (the ones in the tool's enum: geolocation, notifications, camera, microphone, clipboardReadWrite, clipboardSanitizedWrite, sensors). The manifest now declares `"contentSettings"` permission.
- Popup adds a "pending dialog" UI surface with Accept / Cancel buttons (and a prompt input for `prompt` type), polling background every 800 ms while open.
- New dispatcher + event-log tests covering the three tools: forwarding, validation, claim bypass for `dialog_respond`, push-based match + replay window for `wait_for_tab`, subscriber lifecycle (in-flight, replay, no-double-fire, error isolation).

### Agent-facing gotcha

- `window.open()` triggered from a button's `onClick` handler does NOT count as a user gesture when the click was dispatched via `browser.click` (CDP `Input.dispatchMouseEvent`). Chrome's popup blocker silently swallows it (the window handle is non-null but no tab is actually created and `chrome.tabs.onCreated` never fires). The reliable way to trigger a popup-spawning click from an agent is `browser.evaluate({ expression: 'document.querySelector("...").click()' })` — `Runtime.evaluate` with `userGesture: true` (what evaluate uses internally) IS recognised as user activation. Documented in `wait_for_tab`'s `gotchas` array.

## [0.11.0](https://github.com/jobshimo/browser-link/compare/v0.10.0...v0.11.0) (2026-05-18)

### Features

- **bridge:** add `browser.wait_for` MCP tool. Blocks until a condition becomes true on the page before continuing the agent flow. Three mutually-exclusive target modes:
  - `selector` + `condition` (`visible` | `hidden` | `attached` | `detached`, default `visible`) — `visible` means the element exists in the DOM, has a non-zero bounding rect, opacity > 0, and `display !== 'none' / visibility !== 'hidden'`.
  - `expression` — any JS string evaluated each poll; `wait_for` stops as soon as `Boolean(expression)` is truthy. Runs through `Runtime.evaluate` so it is subject to the same disabled-list as `browser.evaluate`.
  - `network_url` — case-insensitive substring matched against the URL of completed network requests in the rolling buffer (last 200). Stops when at least one matching request has finished.
    Returns `{ matched, elapsed_ms, checks, reason? }`. **`matched: false` is NOT an error** — the caller decides whether to proceed or take a plan-B path. Polls every `poll_interval_ms` (default 100, clamped to `[50, 1000]`) until `timeout_ms` (default 5000, capped at 30000 — the bridge does not park requests longer than that). Like the other read tools (`browser.snapshot`, `browser.console`, `browser.network`), `wait_for` does NOT require a tab claim — multiple agents can wait on the same tab in parallel.

### Validation

End-to-end validated on the `browser-link-playground` (`/wait-for` route) with all three modes. Page-observed flip-time correlates with `wait_for`'s reported `elapsed_ms` minus the bridge dispatch latency (the parallel-call delay between `click` and `wait_for` arriving at the extension). `checks` always reflects real polling iterations, never a short-circuit.
