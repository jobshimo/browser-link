# Changelog

## [0.23.3](https://github.com/jobshimo/browser-link/compare/v0.23.2...v0.23.3) (2026-07-12)

### Bug Fixes

- **cdp-direct:** fixed a WebSocket leak in the transport's per-target connection cache — `getConnection` only cached a RESOLVED `CdpClient`, so two concurrent tool calls to the same `cdp:` tab that both missed the cache (routine under multi-agent mode, or one agent issuing parallel calls to the same tab) each opened their own connection, both ran `connect()` + target re-validation + `Page.enable`, and both raced to `connections.set(targetId, ...)` — the second write overwrote the first, leaving the loser's open WebSocket with no map entry at all, invisible to the idle sweep and leaked until process exit. The cache now single-flights the dial: an in-flight `Promise<connection>` is cached per targetId so concurrent callers await the SAME attempt and exactly one socket is ever opened; a FAILED attempt is evicted the moment it settles (rejections are never cached, so the next call retries fresh), and the existing behaviors are preserved unchanged — a cached entry whose client is no longer open (tab closed, WS dropped) is still replaced with a fresh dial on the next call, connect-time target re-validation still runs via the same `isDrivablePageTarget` predicate, and the idle sweep keeps its exact 5-minute-unused / 60-second-interval contract.

### Performance

- **map:** `browser.list_tabs` now resolves the persistent-map hint for ALL connected tabs in one batched lookup instead of one `getMapHint` call (3 synchronous SQL queries: app lookup + 2 COUNTs) per tab — on a tool that runs on nearly every agent turn, N tabs cost 3N queries just for hint enrichment. New `getMapHints(origins)` in `map/queries.ts` resolves every DISTINCT origin in exactly 3 queries total regardless of tab count (`WHERE origin IN (...)` for the app rows with the same `last_seen_at DESC, id DESC` winner-per-origin rule the single lookup used, then one `WHERE app_id IN (...) GROUP BY app_id` COUNT per table); `handleListTabs` batches over the distinct origins of the merged extension + cdp tab list in one call. `getMapHint` is now a thin single-origin wrapper around the batched version, so the two paths share one query shape and cannot drift. The returned `MapHint` shape, the "omit the field rather than ship a zero hint" semantics, and `server.ts`'s degrade-to-no-hints try/catch (a map DB failure must never break tab listing) are all byte-identical to before.

### Internal

- **cdp-direct:** the transport's connection-cache lifecycle — shipped untested in v0.23.0 — is now covered directly in `cdp/transport.test.ts` against the existing fake CDP-over-WS server, counting the sockets the fake server actually accepts: cache reuse across sequential calls, the concurrency race above (verified to FAIL against the pre-fix `getConnection`: two sockets opened, plus a teardown hang from the leaked one), failed-attempt eviction (a dead endpoint does not poison the cache for a later retry), re-dial after the server closes the target's socket, and the idle sweep closing + evicting an unused connection. The idle thresholds are overridable through a test-only `setIdleCleanupConfigForTest` export (restored to the real defaults by `resetConnectionsForTest`) because waiting out the real 5-minute window in a test is not practical.
- **map:** `map-hint.integration.test.ts` (real temp-dir SQLite, real handlers) gains the multi-tab batch paths: several tabs on one origin all carrying the same hint, a mix of tabs with and without a saved app, and a per-tab equivalence assertion that the batched `list_tabs` result matches the single-origin `getMapHint` for every tab's origin.

## [0.23.2](https://github.com/jobshimo/browser-link/compare/v0.23.1...v0.23.2) (2026-07-12)

### Bug Fixes

- **config:** `idleTtlMinutes` and `cdpDirectGrantTtlMinutes` are now clamped at the `loadConfig()` read boundary, the same trust-boundary treatment `cdpDirectPort` already gets via `sanitizeCdpPort` — `withDefaults` previously defaulted both with a plain `??`, which only catches null/undefined, so a corrupted or hand-edited `config.json` value (a string like `"abc"`, a negative number, a float, an absurdly large value like `1e9`) flowed unclamped into `browser-link config get idle-ttl`, the `settings.update` WS push to the extension, and `config get cdp-direct.grant-ttl`. Both fields now pass through their existing `clampIdleTtlMinutes` / `clampGrantTtlMinutes` (garbage falls back to the default rather than snapping to a boundary — their documented behavior), so every consumer reads a valid value by construction. `0` ("never") still survives untouched for both fields, and `idleTtlMinutes` keeps its "never touched by the CLI" `undefined` sentinel — it is only clamped when a value is actually present, so a popup-only user still reads as "not set via CLI" and never sees a spurious server-side default pushed over their own choice.
- **auth:** raised the silent-debugger-flag detection timeout (`DETECT_TIMEOUT_MS` in `auth/silent-debugger.ts`) from 3000ms to the 5000ms budget `process-identity.ts`'s `LOOKUP_TIMEOUT_MS` already documents from production (tasklist-class tools observed at ~3s on loaded Windows machines). The Windows path shells out to PowerShell `Get-CimInstance Win32_Process` — WMI, a slow cold start — and silently degrades to `{ detected: null }` ("could not determine") on timeout, so the old 3s budget made `browser-link doctor` routinely fail to report the infobar status on exactly the loaded machines that most need it. No like-for-like fallback chain is possible here: the probe needs full command lines to find `--silent-debugger-extension-api`, which neither `Get-Process` nor `tasklist` expose; a `wmic process` second attempt was evaluated and rejected (it queries the same WMI subsystem that just timed out, and wmic is deprecated and absent on newer Windows 11 installs) — the reasoning is documented in the code. The exec step is now injectable (`ExecLike`, defaulting to the real `execAsync` on every production call path), with unit tests covering timeout, exec error, flag present/absent, and the unsupported-OS path.
- **map:** `browser-link map forget <app> --flow` with no value after `--flow` now errors with a clear usage message (`--flow requires a flow name`, EN and ES) and a non-zero exit instead of silently widening scope to the whole app — `parseArgs` treats a valueless `--flow` as boolean `true`, so `flowName` resolved to `undefined` and execution fell through to the whole-app forget path, giving a user who merely forgot the flow name a whole-app dry-run (or, with `--yes` also present, an actual whole-app deletion). The guard rejects before any DB lookup, so nothing is resolved, touched, or printed beyond the error; `--flow <name>` is unaffected.

## [0.23.1](https://github.com/jobshimo/browser-link/compare/v0.23.0...v0.23.1) (2026-07-12)

### Bug Fixes

- **recorder:** right-click (context menu) and middle-click were recorded as ordinary left clicks — neither `onPointerDown` nor `onClick` in `inpage/recorder.ts` checked `ev.button`, so opening a context menu on an element produced a `{kind:'click'}` step indistinguishable from a real left click, corrupting any recipe captured near a right-click. Both handlers now bail unless `ev.button === 0`. The same gate also applies to gesture authorization: `onMouseDown`'s `noteTrustedPointer` call (which feeds the type-commit gesture-correlation gate) previously ran for ANY trusted button, so a right-click on a text field — e.g. to open the paste menu — followed by focus loss still emitted a `{kind:'type'}` step; a non-left mousedown no longer notes a gesture, so only a primary-button interaction (or a trusted key event while focused) can authorize a type-commit.
- **recorder:** holding a key down fired OS key-repeat keydowns that were each recorded as their own `press` step, burning through the 20-step recording budget on a single held key (e.g. holding Arrow Down to scroll a list). `onKeyDown` now bails on `ev.repeat`, so only the initial keydown for a keystroke is captured.
- **recording:** `MAX_RECORDING_STEPS` in `recording.ts` was a second hardcoded `20` that merely happened to match `MAX_FLOW_STEPS` (the server's actual `browser.flow` schema ceiling, already exported from `flow.ts`). It now imports and re-exports that constant directly, so the recording cap and the replay cap can never silently drift apart from a future edit to either literal.
- **extension:** Discard did not cancel a Save already in flight. `saveRecording` stashes its resolver on `state.pendingFlowSave` and awaits the server's `flow.recorded.result` (or a 10s timeout); `clearRecording` (Discard's teardown path) cleared `state.recording` but left that resolver untouched, so a late, successful server response ran its success continuation as if nothing had happened — the popup told the user the capture was discarded while the recipe was, in fact, saved. `clearRecording` now settles any pending save immediately as a failure, and `saveRecording`'s success continuation additionally checks the recording session's identity (a nonce comparison, extracted as the pure, unit-tested `isSameRecordingSession`) before tearing down state, so a stale response can never wipe a brand-new recording the user started on the same tab in the meantime. Known, documented limitation: if the `flow.recorded` request had already reached the server before Discard ran, the server may have already validated and persisted the flow — there is no server-side "unsave," so this fix only guarantees the extension's own state is consistent, not that a fast-enough save is retroactively undone.
- **extension:** `startRecording` leaked a CDP binding on every retried Record click after a failed injection — if `Runtime.addBinding` succeeded but the subsequent `injectRecorder` call threw (e.g. a page CSP blocking the injected script), nothing ever called `Runtime.removeBinding` for that orphaned session, since the normal removal path only runs for a recording that actually reached `state.recording`. Failed injection now best-effort rolls the binding back, without letting a rollback failure mask the original error.
- **server:** `handleFlowRecordedMessage` validated `name` and `description` against their declared runtime shape but passed `origin` straight through to `saveFlow`/`canonicalOrigin` unchecked. `payload` arrives over the wire as an unvalidated `JSON.parse` cast, so a non-string `origin` would either get silently coerced by `new URL()` into an unrelated string or fall through `canonicalOrigin`'s catch-all and land in the map completely as-is — a bogus value indistinguishable from a real origin. `origin` now gets the same `typeof`/non-empty check its neighbors already have.

## [0.23.0](https://github.com/jobshimo/browser-link/compare/v0.22.0...v0.23.0) (2026-07-11)

### Security

- **cdp-direct:** sanitize the `cdp-direct.port` config value at the trust boundary before it reaches any URL, fixing a config-driven SSRF breakout that CI's CodeQL flagged (`js/file-access-to-http`, 2 alerts). `cdp-direct.port` is read from `config.json` (untrusted — hand-edited or corrupted) and was interpolated raw into `http://127.0.0.1:<port>/json/version|list` and `ws://127.0.0.1:<port>/devtools/page/<id>`; the old `?? 9222` fallback only caught null/undefined. A value like the STRING `"9222@attacker.com"` would, by URL userinfo syntax, resolve to host `attacker.com` — an off-host request despite the hardcoded loopback literal. New `sanitizeCdpPort(raw: unknown)` (config.ts) coerces with `Number()` (NOT `parseInt`, which would read `"9222@…"` as `9222` and accept it) and returns the value only when it is a whole port in `[1, 65535]`, else the default 9222 — always a fresh validated integer, never the raw text. Applied once in `loadConfig`'s `withDefaults` so `cfg.cdpDirectPort` is valid by construction for every consumer, AND again at each URL-construction site (`cdp/targets.ts` discovery, `cdp/transport.ts` ws URL, `commands/cdp.ts` status) as defense in depth. Discovery/connection URLs are additionally built via `new URL()` with an asserted `hostname === '127.0.0.1'` before any `fetch`/connect — a second barrier that refuses an off-host request even if a future port value slipped validation. Covered by tests proving a hostile port (`"9222@attacker.com"`, `"9222/x"`, `0`, `70000`, a float, a bare hostname, …) never produces a fetch to a non-loopback host and always falls back to 9222, while a valid custom port (9333) is used verbatim.

### Features

- **cdp-direct:** extension-free transport — the server can now drive Chrome tabs DIRECTLY over a user-launched `--remote-debugging-port` (default 9222), as a faster alternative to the `chrome.debugger`/extension path, gated so an agent can never reach it without explicit, time-boxed human consent. Two independent opt-ins are required before any tool may address a `cdp:` tab: (1) `cdp-direct.enabled` (`browser-link config set cdp-direct.enabled true`, off by default, loopback port configurable via `cdp-direct.port`, default 9222 — the host is never configurable, always `127.0.0.1`) and (2) a live grant recorded by the new `browser-link cdp allow [--minutes N]` (default lifetime `cdp-direct.grant-ttl`, 60 min, clamp 1-1440, `never`/`0` allowed but documented as reducing the security posture), revocable any time with `browser-link cdp revoke`, inspectable with `browser-link cdp status` (enabled?, port, grant state + remaining time, whether a Chrome DevTools endpoint is reachable right now). An agent hitting a `cdp:` tab with either condition unmet gets exactly one of two fixed error strings naming the missing step and the exact command to fix it (`cdp-direct is disabled. The user can enable it with: browser-link config set cdp-direct.enabled true` / `cdp-direct requires an active grant. Ask the user to run: browser-link cdp allow`) — there is no bypass.
- **bridge:** when enabled AND granted, `browser.list_tabs` additionally returns page targets discovered from `http://127.0.0.1:<port>/json/list`, each carrying `tab_id: "cdp:<targetId>"` and `transport: "cdp"` so agents can tell the two transports apart; the endpoint is verified as genuinely Chrome via `/json/version`'s `Browser` string first, and `devtools://`/`chrome-extension://` targets are filtered out. Extension tabs are completely unaffected — same shape, same behavior, byte-equivalent dispatch path. v1 tool support over cdp-direct: `list_tabs`, `ping`, `snapshot`, `find`, `state`, `click` (occlusion guard + settle included, unchanged — they are in-page logic), `type`, `press`, `evaluate`, `wait_for` (`selector`/`expression` modes; `network_url` mode is out of scope — no network buffering over this transport), `navigate`, `flow`. `browser.drag`, `browser.console`, `browser.network`, `browser.network_body`, `browser.canvas_screenshot`, `browser.dialog_respond`, `browser.set_permission` and `browser.wait_for_tab` return a clear "not supported over cdp-direct in v1 — use a tab connected through the Chrome extension instead" error naming the fallback. Tab claims (`browser.claim_tab`/`release_tab`/`my_tabs`) and the persistent map's origin-keyed `list_tabs` hint enrichment work identically on `cdp:` tab_ids — both are transport-agnostic by construction.
- **docs:** new README section "cdp-direct mode (no extension)" — what it is, the security tradeoff against the extension's per-tab consent + infobar transparency (links the existing yellow-bar FAQ), the exact `enable → allow → use → revoke` command flow, and the v1 tool-support table. `browser-link about`/`browser-link cdp`/`browser-link config` EN/ES help text documents the same. `agent-instructions/content.ts`'s trigger block and `tools/server-instructions.ts`'s preamble teach agents how to recognize a `cdp:` tab, which tools are unsupported on it in v1, and that the two gate errors mean "relay the suggested command to the user — there is no workaround."

### Internal

- New `packages/server/src/cdp/` module: `client.ts` (`CdpClient` — minimal CDP-over-WebSocket client, JSON-RPC-style request/id correlation, event subscription; mock-tested against a real ephemeral `WebSocketServer` fake target, no real Chrome required in CI), `targets.ts` (discovery + `/json/version` product verification + the `cdp:`/`tab_id` <-> target-id helpers), `transport.ts` (the tool-routing adapter — a per-target connection cache with idle cleanup, mirroring `packages/extension/src/background.ts`'s `handleTool` switch and its extracted `performFind`/`performClick`/`performType`/`performPress`/`performWaitFor` helpers function-for-function, over the raw CDP client instead of `chrome.debugger`), `support.ts` (the single declarative v1 tool-support table, a `Map` rather than a `Record` so an unlisted tool types as genuinely `undefined` — same reasoning `keymap.ts`'s `NAMED_KEYS_LOWER` already documents), `grant.ts` (grant file read/write/clear in the data dir), `gate.ts` (the two-step enabled+grant check, the single source of truth for both fixed error strings). `inpage/deep-query.ts`, `inpage/dom-helpers.ts`, `inpage/builders.ts` (the snapshot/find/click/type/focus/settle/state builders — `buildDragProbeJs` deliberately NOT copied, drag is out of v1 scope), `settle.ts`, `keymap.ts` and `flow.ts` are independent verbatim copies of their `packages/extension/src/` counterparts — the server publishes to npm standalone and cannot carry a workspace dependency on `@browser-link/extension` (a private, unpublished package), the same reasoning `config.ts`/`messages.ts` already document for their own in-tree duplicates. Every copied module is `chrome.*`-free by construction (they build JS-source strings or CDP command parameters, nothing more), so the duplication is mechanical, not a fork of behavior.
- `tools/browser-dispatch.ts` gains one routing seam, `routeToolCall` (used by `runAction` and every direct read-tool call site), that inspects the tab_id prefix and enforces the gate + `cdp/support.ts` table for `cdp:` tabs before ever calling `deps.callCdpTool` — the extension path (`deps.callBrowserTool`) is an unmodified passthrough for every non-`cdp:` tab_id. `BrowserToolDeps` gains three optional members (`listCdpTabs`, `callCdpTool`, `cdpGate`) so existing test fixtures and any build without cdp-direct wired up keep compiling unchanged. `handleListTabs` becomes async, merging `deps.listCdpTabs()` into `deps.listTabs()`'s result before the existing claim/map-hint enrichment loop — enrichment itself needed no changes, being origin/tab_id-keyed already. `browser.wait_for_tab` gates on `opened_from` when it is a `cdp:` id (a new tab opened FROM a cdp-direct tab produces no bridge event to wait on) before ever touching `subscribeEvents`.
- `config.ts` gains `cdpDirectEnabled`/`cdpDirectPort`/`cdpDirectGrantTtlMinutes` on `BrowserLinkConfig` (defaulted false/9222/60 via `withDefaults`, stripped back to nothing in `normaliseForWrite` when they match those defaults — same diff-friendly-file convention `multiAgent`/`autoReelect` already established) plus `clampGrantTtlMinutes`/`clampCdpDirectPort` defensive fallbacks (corrupted/hand-edited config.json values fall back to the default rather than snapping to a boundary, mirroring `clampIdleTtlMinutes`'s own reasoning). New `commands/cdp.ts` (`allowCdpDirect`, `revokeCdpDirect`, `cdpDirectStatus`, `runCdpCommand`) wired into `cli.ts`'s dispatch switch and both EN/ES help blocks. `commands/config.ts` grows `cdp-direct.enabled`/`cdp-direct.port`/`cdp-direct.grant-ttl` as the first DOTTED config keys the `get`/`set` parser accepts, reusing `parseGrantTtlArg`'s exact clamp-with-note wording (exported) for both `config set cdp-direct.grant-ttl` and `cdp allow --minutes`'s per-call override — one implementation of "what counts as a valid TTL argument."
- Security hardening from the pre-ship adversarial review (permission gate itself verified airtight, no bypass): (1) `revoke` now fails CLOSED. `clearGrant` no longer swallows an `unlinkSync` failure, and — because the realistic Windows failure is a lock that blocks DELETION while the grant file stays READABLE (so `loadGrant` reads it fine and the gate would keep passing it) — `revokeCdpDirect` ALSO flips `cdp-direct.enabled=false` (a DIFFERENT file, config.json, unlikely to share the grant's lock) as a defense-in-depth fallback, so the gate's FIRST check denies even though the stale grant survives. Reported honestly (`Could not remove the grant file: <path> — <reason>. As a safeguard, cdp-direct has been DISABLED …`, EN/ES) with a non-zero exit; if disabling ALSO fails, both facts are surfaced loudly (`… cdp-direct MAY STILL BE ACTIVE …`). A test proves the gate DENIES after an unlink-fails-but-file-readable revoke. (2) `getConnection` re-validates the target on CONNECT via `Target.getTargetInfo`, not just at discovery — the transport is reached by a caller-supplied `cdp:<targetId>` whose provenance is untrusted (need not have come from a `list_tabs` this process produced), so it refuses any non-page / devtools / extension surface using the SAME `isDrivablePageTarget` predicate discovery uses (extracted + shared so the two checks cannot drift), before enabling any CDP domain on it. (3) `callCdpTool`'s per-tool `timeoutMs` is documented as deliberately NOT wrapped in an outer race — every underlying step already carries its own hard bound (15s per CDP command, 20s navigation load wait, ≤30s wait_for poll, ≤60s flow budget), so an outer timer would only add a redundant failure mode; the parameter is kept for signature parity.
- Known, documented tradeoff: `browser.flow` gates once at entry and then runs all its steps; a `cdp allow` revoked MID-flow does not interrupt an already-running flow (bounded to the flow's ≤60s worst-case budget — the next tool call after it returns sees the revoked grant). Every non-flow tool call re-checks the gate fresh. Documented in the README's cdp-direct section and NOT changed in code, to preserve `cdp/flow.ts` as a byte-identical copy of the extension's transport-agnostic flow engine (a per-step gate re-check would fork it). A future v2 could add per-step gating alongside console/network mirroring, canvas capture and drag (the other deferred v1 items).
- Verbatim-copy drift guard: `cdp/drift.test.ts` fails the build if the injected `DEEP_QUERY_JS` / `DOM_HELPERS_JS` bodies (the security-relevant DOM visibility / selector-generation / occlusion / deep-traversal logic) ever diverge byte-for-byte from their `packages/extension/src/inpage/` originals, and if the numeric safety invariants of `settle.ts` / `flow.ts` / `keymap.ts` drift — closing the "a security fix to one copy silently misses the other" gap the flow-recorder work highlighted. `cdp/builders-parity.test.ts` additionally asserts the (subset) in-page builder copies emit byte-identical OUTPUT to the extension originals for the same inputs (a full output-identity check, not just the embedded shared bodies). Each copied module's header names its exact sibling path and points at the guard.
- Test coverage: `cdp/client.test.ts` (10 cases against a real ephemeral fake CDP-over-WS server — request/response correlation, error propagation, timeouts, concurrent-by-id correlation, event subscription + unsubscribe, connection-closed rejection), `cdp/grant.test.ts` (incl. the unlink-failure surfacing), `cdp/gate.test.ts`, `cdp/support.test.ts`, `cdp/targets.test.ts` (discovery gating, product verification, devtools/extension-page filtering, `isDrivablePageTarget`), `cdp/transport.test.ts` (tool dispatch against a fake single-target server — ping/evaluate/navigate/click/press, permission-gate + malformed-tab_id + out-of-scope-tool + non-page-target-at-connect rejections), `cdp/drift.test.ts` + `cdp/builders-parity.test.ts` + local execution tests for the copies (`cdp/keymap.test.ts`, `cdp/settle.test.ts`, `cdp/flow.test.ts`, `cdp/inpage/builders.test.ts`), `commands/cdp.test.ts` (incl. the fail-closed revoke path proving the gate DENIES after an unlink-fails-but-readable revoke, and the both-failed case, EN/ES), `config.test.ts` (new, the clamp functions + defaults/persistence round trip), plus additions to `commands/config.test.ts` and `tools/browser-dispatch.test.ts` (cdp routing: byte-equivalent extension path, gate enforcement, unsupported-tool rejection, `list_tabs` merge, `wait_for_tab` gating).

## [0.22.0](https://github.com/jobshimo/browser-link/compare/v0.21.0...v0.22.0) (2026-07-11)

### Features

* **extension:** record a `browser.flow` recipe by demonstrating it once in a connected tab, instead of hand-writing one. STRICTLY OPT-IN and off by default: a new "Enable flow recording" popup toggle (persisted in `chrome.storage.local`, editable via `browser-link config get/set flow-recording <on|off>` through the same settings-sync machinery the idle-disconnect TTL already established — server config, IPC `settings.push`, WS `settings.update`, last-write-wins by `updatedAt`, now generalized to carry either setting's pair independently) gates whether the in-page recorder is ever injected at all. Once enabled and a tab is connected, the popup shows Record/Stop; while recording, an in-page script (`inpage/recorder.ts`, injected via CDP `Runtime.evaluate` only for the session) captures clicks (pointerdown primary signal, deduped against the following click), one type-commit per focused text field on blur/change/Enter (the payload carries only the field's generated selector — there is no field capable of carrying the value the user typed), and non-commit special keys (Escape/Tab/arrows) as `press` steps, reporting each over a CDP binding (`Runtime.addBinding`, which — unlike the in-page script itself — survives navigations automatically; the recorder script is re-injected after every navigation observed via the same `chrome.tabs.onUpdated` signal `browser.navigate` already uses). A navigation mid-recording inserts an editable `{wait_for:{expression:"document.readyState === 'complete'"}}` suggestion. Capped at 20 steps, matching `browser.flow`'s own ceiling — recording auto-stops with a popup notice at the cap. Stop shows a step-by-step review with a name input; Save sends the recipe to the server (`flow.recorded`), which validates it with the EXACT `validateFlowSteps` rules `browser.flow` itself enforces, persists it into the same `flows` table `browser.map.save({ flows })` writes to (canonicalizing the origin the normal way), and emits a server-owned `flow-recorded` bridge event so `browser.events` surfaces the new recipe — a validation failure is shown in the popup instead of silently vanishing. No new MCP tool surface: agents keep discovering and replaying recorded recipes through the existing `browser.map.recall` → `browser.flow` loop, exactly as a hand-written recipe. Turning the toggle off — from the popup, or a losing `settings.update` race — force-stops and DISCARDS any in-progress recording across every tab immediately, and the recorder's own listeners are torn down the moment recording stops (Stop, Discard, disconnect, or the setting flipping off). README gains a "Recording flows by demonstration" section documenting the capture grammar and these privacy properties as verifiable facts, not just promises.

### Security

* The recorder reaches the extension through a CDP binding, which is a global function reachable by EVERY script in the target page (the site's own code, ads, third-party widgets, an XSS payload). The recorder is hardened so the feature is safe to leave enabled while browsing arbitrary pages, closing several would-be holes: (1) a hostile page fabricating steps or using the binding as an EXFILTRATION primitive (e.g. `{kind:'type', selector: document.cookie}`); (2) page-synthesized events (`el.click()`, `dispatchEvent(...)`) being captured as real user actions; and (3) the focus/blur trusted-event bypass — unlike `.click()`, a programmatic `element.focus()`/`.blur()` from page script fires focus/blur events with `isTrusted:true`, so the `isTrusted` gate alone did NOT stop a page from `attackerInput.focus(); attackerInput.blur()` to fabricate a `{type, selector}` step for an attacker-chosen replay target. Defenses: a fresh per-recording-session NONCE and, for the recorder's in-page globals (CDP binding + idempotency flag + teardown hook), THREE independent bare random identifiers with no shared prefix or suffix (all from `generateRecordingSession()`, interpolated into the injected source, known only to the recorder and the extension process) — every payload carries the nonce and `parseRecordedPayload` discards any that lacks it, so a blind page-script call records nothing, and a page cannot cheaply scan `window` for a predictable pattern (e.g. the old `__blRec_` prefix) to detect that recording is active; a `!event.isTrusted` guard at the top of every recorder listener; a GESTURE-CORRELATION gate for type-commits (a `type` step is emitted only when the field's focus was driven by a real trusted pointer gesture on it or a trusted key event while focused — a focus/blur pair with no such gesture is dropped, defeating the focus/blur bypass); stricter-than-`browser.flow` validation of recorder payloads (selector length-capped and rejected on control characters — C0/C1 controls, ZWSP, line/paragraph separators, legacy bidi embed/override and modern bidi isolate controls, WORD JOINER and BOM — but NOT ZWJ or LRM/RLM, which appear in legitimate emoji and RTL-aware aria-labels, so the channel cannot smuggle a token disguised as a selector into the map while a real emoji/directional-mark label still records, `press` keys restricted to the exact recorder allowlist); a server-side `flow.recorded` `tab_id` check against the submitting connection's registered id; and recorded name/description length caps. Recorder page listeners are torn down in-page on EVERY exit path — Stop, Discard, disconnect, tab removal, idle-sweep cleanup, and the setting flipping off — because `chrome.debugger.detach` drops the CDP binding but NOT the plain `window.addEventListener` listeners. The genuinely ambiguous-selector signal `genSelectorInfo` computes is surfaced (per-step ⚠ in the popup review list, folded into the saved recipe's description) rather than silently dropped. The README privacy section states the threat model honestly: the nonce + `isTrusted` gate + gesture correlation are the real defenses, the review list is a usability aid and not a detection surface, and the residual risk (a script that can read the recorder closure's own variables already owns the page outright) is stated plainly. ## [0.17.0](https://github.com/jobshimo/browser-link/compare/v0.16.0...v0.17.0) (2026-07-11)

### Features

- **bridge:** new `browser.flow` tool — runs a declarative sequence of `find`/`click`/`type`/`press`/`wait_for` steps in ONE round trip instead of one MCP call per step. A common UI task (locate a target, click it, wait for a result, fill it in, submit) used to cost an agent 5-10+ sequential MCP round trips — each one a full LLM inference — before it could report back. With `browser.flow`, the same task is one call (two if a step fails and a corrective follow-up is needed). Steps run strictly in order and fail fast: the first failing step stops the flow immediately, there is no branching. A `find` step's resolved selector becomes the IMPLICIT TARGET for the very next `click`/`type`/`press` step that omits its own `selector` — an explicit `selector` on that step always overrides it and leaves the implicit target untouched for a later step to consume. `type` and `press` steps that end up with no selector at all (no explicit one, no implicit one) act on whatever currently has focus, exactly like standalone `browser.press`; only `click` truly requires a resolved target, since there is no "click whatever has focus" concept. `click`/`type`/`press` steps default `settle_ms` to 150, same as the standalone tools. Example (GIF picker): `{find:{text:"GIF",role:"button"}}, {click:{}}, {wait_for:{selector:"[data-testid=gif-search]",condition:"visible"}}, {type:{selector:"[data-testid=gif-search]",text:"shrek"}}, {press:{key:"Enter"}}` — 5 steps, 1 round trip. On success returns `{ ok: true, steps_completed, results }` with a compact per-step result (`{selector}` for `find`, `{ok, settle?}` for everything else). On failure returns `{ ok: false, failed_step, step_kind, error, steps_completed, recovery_snapshot }` — `error` is the same message the standalone tool would have returned for that failure, and `recovery_snapshot` is a focused `browser.snapshot({only_interactive:true, max_interactive:40})` of the page as it stands, so the agent sees where the flow stopped without a follow-up round trip. `evaluate` and `navigate` are deliberately NOT flow steps in v1 — arbitrary JS inside a flow raises permission-model questions this tool does not solve yet, and a mid-flow navigation can tear down the very document later steps expect to act on. Action tool: participates in the tab-claim layer exactly like `browser.click`/`browser.type`/`browser.press`.

### Internal

- Extension: the `click`/`type`/`press`/`find`/`wait_for` case bodies in `background.ts` are extracted into standalone `performClick`/`performType`/`performPress`/`performFind`/`performWaitFor` functions returning a structured `ActionOutcome<T>` (`{ok:true,result} | {ok:false,error}`) instead of a wire-level `tool.response`. ## [0.16.0](https://github.com/jobshimo/browser-link/compare/v0.15.0...v0.16.0) (2026-07-11)

### Features

- **bridge:** new `browser.press` tool — dispatches a single trusted key press (optionally with modifiers) via CDP `Input.dispatchKeyEvent`, producing real `isTrusted: true` keyboard events. Until now, the only way to send Enter/Escape/Tab/arrow keys was a synthetic `KeyboardEvent` through `browser.evaluate` — this repo's own v0.14.0 CHANGELOG already documents, empirically, that Qt-WASM discards synthetic input, and the same is true of many rich text editors and autocomplete widgets that check `event.isTrusted` before acting. `key` accepts a human name (`Enter`, `Escape`, `Tab`, `Backspace`, `Delete`, `ArrowUp`/`ArrowDown`/`ArrowLeft`/`ArrowRight`, `Home`, `End`, `PageUp`, `PageDown`, `Space` — case-insensitive) or a single printable character (case-sensitive, `"a"` vs `"A"`, plus common punctuation and shifted digit-row symbols). `modifiers` is an array of `Alt`/`Control`/`Meta`/`Shift`, encoded as the CDP bitmask, for shortcuts like Ctrl+A or Cmd+S. An optional `selector` focuses an element first through the same deep Shadow DOM / iframe search `click`/`type`/`find` already use; omitted, the key goes to whatever currently has focus. Implementation dispatches a `keyDown`-or-`rawKeyDown` / `char` / `keyUp` sequence — `rawKeyDown` only when the key produces no text (control/navigation keys), keeping the `char` event as the single source of actual text insertion so nothing double-types. `Enter` carries text `\r` (matching Puppeteer's `USKeyboardLayout`), so its `char` event produces the KEYPRESS whose default action drives the WHATWG implicit form submission — pressing Enter in a form field actually submits the form. Shift is auto-added for characters that require it on a US layout (uppercase letters, shifted punctuation like `@`), so `key:"A"` types an uppercase A without an explicit modifier. Action tool: participates in the tab-claim layer exactly like `browser.click`/`browser.type`.
- **bridge:** `browser.click`, `browser.type` and `browser.press` accept an optional `settle_ms` (default 150, max 2000; `0` disables) and `settle_timeout_ms` (default 2000, max 10000). After dispatching, the extension installs one `MutationObserver` on `document` (subtree, childList, attributes, characterData) and waits until no mutation lands for `settle_ms` consecutive milliseconds, capped at `settle_timeout_ms`. The result gains a compact `settle` object — `{ settled, duration_ms, mutation_count, url_changed?, focus_moved? }` — with `url_changed`/`focus_moved` present only when they actually changed during the wait. This folds the wait_for + snapshot round trip most flows need after an action directly into the action call: a click that triggers an async re-render no longer needs a separate `browser.wait_for` just to know the page settled. Purely additive — existing result fields are unchanged, and `settle_ms:0` reproduces the pre-v0.16.0 behavior exactly (no extra round trip, no `settle` key in the result). The occlusion guard on `browser.click` is untouched — settle only runs after a successful dispatch. The settle wait is failure-isolated from the action: when the action itself triggers a full-document navigation, the execution context the settle expression runs in is destroyed mid-wait — the action result stays `ok:true` (it DID land) and `settle` degrades to `{ settled: false, reason: "context-destroyed" }` instead of the whole call flipping to an error that would bait a duplicate retry. Honest limitation, documented on the tools: settle proves QUIET, not EFFECT — mutations completing before the observer installs (right after dispatch) and async reactions starting after the quiet window are both invisible, so `mutation_count: 0` with `settled: true` does not prove the action had no effect; `browser.wait_for` remains the tool for a specific expected condition.

### Features

- **bridge:** `browser.snapshot`, `browser.find`, `browser.click` and `browser.type` now pierce OPEN Shadow DOM roots and same-origin iframes, nested arbitrarily (shadow roots inside iframes and vice versa). Previously all four walked the DOM with plain `document.querySelector` / `querySelectorAll`, so anything behind an `attachShadow({ mode: "open" })` boundary or inside an in-page iframe was invisible to agents. The scan enumerates every reachable root and queries each independently; selectors returned by `snapshot`/`find` are verified unique across the FULL deep search scope before being handed out, so the find → click round trip keeps working when the target lives inside a web component or iframe. Entries for iframe-hosted elements carry an optional `frame` field (the CSS selector of the innermost hosting iframe) — the result shape stays backward compatible.
- **bridge:** `browser.click` gains an occlusion guard. Before dispatching CDP mouse events, the click point is hit-tested starting from the target's own root (shadow root or iframe document, descending nested open shadow roots). If a different element covers the point — modal backdrop, loading overlay, dropdown — the call returns `ok:false` with `Element covered by <tag#id.class> — click the covering element or dismiss it first` instead of silently clicking the wrong thing. Clicks on the target itself, its own descendants, or a wrapper containing it (composed-tree containment) pass. A new optional `force: true` parameter skips the guard as a documented escape hatch. `pointer-events: none` overlays never block (elementFromPoint skips them natively).
- **bridge:** correct coordinate mapping for iframe-hosted elements. CDP `Input.dispatchMouseEvent` takes TOP-LEVEL viewport coordinates; clicks and `find` coords now accumulate each ancestor iframe's bounding rect PLUS its border and padding (the embedded document's viewport origin sits at the frame's content box, not its border box). Every ancestor iframe is scrolled into view alongside the target before measuring.
- **bridge:** click point accuracy for line-wrapped inline elements. The center of `getBoundingClientRect()` for a link wrapped across two lines can land in the unpainted gap between line boxes — hit-testing there reported a false blocker and dispatching there missed. Both the occlusion hit-test and the dispatched CDP coordinates now use the center of the FIRST client rect (`getClientRects()[0]`), which is always a painted fragment; they are guaranteed to be the same point.

### Known limitations

- CLOSED shadow roots (`attachShadow({ mode: "closed" })`) are unreachable from page-world JS — `element.shadowRoot` is `null` by design and there is no CDP-level workaround via `Runtime.evaluate`.

- Two structurally-identical component twins in different roots (byte-identical shadow internals, no id/testid/label) cannot be told apart by any CSS selector — no syntax scopes a selector to one root. ## [0.14.0](https://github.com/jobshimo/browser-link/compare/v0.13.4...v0.14.0) (2026-05-20)

### Features

- **bridge:** new `browser.canvas_screenshot` tool. Captures a `<canvas>` element from the connected tab as PNG/JPEG and returns it base64-encoded. Designed for pages whose visible UI is rendered to a canvas — Qt for WebAssembly (Victron VRM Remote Console, Venus OS, Felgo apps), WebGL games, custom rendering engines — where `browser.snapshot` and `browser.find` return nothing useful because there is no DOM inside the canvas to inspect. ### Rationale

Acting on a canvas page is intentionally NOT exposed yet. Implementing that needs careful design around per-tool permissions and the existing claim layer; it will land in a future release. The screenshot tool delivers the immediate value (the LLM can SEE the page) without dragging the security review of the input path along with it.

Encapsulates the visibility / ARIA / multi-match patterns that agents otherwise hand-roll inside `browser.evaluate`, and crucially covers the "peruvian markup" case where the clickable thing is a `<div onclick>` instead of a `<button>` (the naive `querySelectorAll('button').find(b => b.textContent.includes(...))` MISSES it silently — no error, no match, a `?.click()` that does nothing). Selector heuristic is the SAME one `browser.snapshot` uses (extracted into a shared `DOM_HELPERS_JS` so both tools stay consistent).

- **bridge:** `browser.snapshot` accepts optional filters — `within_selector` restricts the scan to a subtree, `only_interactive` skips headings + the visible-text dump, `exclude: ['nav', 'footer', 'header', 'aside']` drops repeated landmarks, `max_interactive` overrides the cap of 120 (hard ceiling 500). Filters are applied IN-page inside the snapshot JS so the dropped material never traverses CDP → bridge → MCP at all. Additive, no breaking change for calls that omit them.

- **bridge:** snapshot serializer omits empty-string fields per entry — `placeholder`, `aria_label`, `name`, `type`, `href`, `value`, `text`, plus `disabled: false`. Roughly 30–40% smaller payloads on every snapshot, even without filter args. Read by key with optional-chaining; consumers depending on `entry.placeholder === ''` need to fall back to `?? ''`.

- **server boot:** logs a one-line warning when any agent-instructions block on disk is older than the running server's VERSION. The mechanism was already there for the CLI / UI surfaces — boot-time log makes it surface without the user having to remember to run `browser-link instructions`. Format: `Agent instructions OUTDATED for N client(s) — <names>. Run \`browser-link instructions install\` to refresh the global .md blocks.` Best-effort: a per-installer filesystem failure is logged and skipped, never aborts server start.

- **agent-instructions:** new `TOKEN-EFFICIENT PATTERNS` section in the CLAUDE.md / AGENTS.md block. Names the two new dedicated tools (`browser.find`, `browser.snapshot` with filters) and writes down the evaluate-recipe patterns that stayed as recipes — batched DOM reads, scrolling, special keys, events cursor. The reason these did NOT become tools is now in writing: every one of them is a single-line `browser.evaluate` away, plus `browser.type` already covers typing through the native setter. Version stamp bumps to v0.13.0; older installs will show `installed-outdated` on the next `browser-link instructions` / startup check.

- **server-instructions:** same `Token-efficient patterns` block added to the MCP `initialize.instructions` PREAMBLE so agents see the patterns at every session start, not only after `browser-link instructions install` ran. Calls out `browser.evaluate` as the escape hatch and pushes agents toward the dedicated tool for each pattern.

### Internal

- `SNAPSHOT_JS` was replaced by `buildSnapshotJs(opts)`. Shared DOM helpers (`isVisible`, `shortText`, `safeCss`, `genSelector`, `accessibleText`) are now in a single `DOM_HELPERS_JS` template injected into both `buildSnapshotJs` and the new `buildFindJs`. Removes the long-standing risk of `snapshot`'s selector heuristic and a hand-rolled `find` heuristic drifting apart.

## [0.12.0](https://github.com/jobshimo/browser-link/compare/v0.11.0...v0.12.0) (2026-05-18)

### Features

- **bridge:** popup-aware bridge — three new MCP tools so agents can survive (and use) the things that block tabs.
  - `browser.dialog_respond({ tab_id, accept, prompt_text? })` — respond to a native `alert` / `confirm` / `prompt` / `beforeunload` dialog. browser-link does NOT auto-dismiss anymore: when CDP reports `Page.javascriptDialogOpening`, the extension emits a `dialog-opening` event in `browser.events` (`{ tab_id, type, message, default_prompt }`) and leaves the dialog open. The agent reads it, decides, and answers. Bypasses the claim guard so any agent observing can unfreeze a tab. The popup also exposes Accept / Cancel buttons as a manual escape hatch for when no agent has this tool in its preset.
  - `browser.wait_for_tab({ opened_from, url_substring?, timeout_ms? })` — block until a new tab spawned by a previous action on a connected tab appears in the bridge stream. The extension auto-connects any tab whose `openerTabId` is already connected (via the same `Connect` flow the popup uses), then emits `tab-created` with `opened_from = the opener's server tab id`. `wait_for_tab` polls the stream and, on match, **auto-claims** the new tab under the calling agent — the wait IS the explicit intent. Returns `{ matched, tab_id?, url?, elapsed_ms, checks, claimed?, claim_conflict?, reason? }`.
  - `browser.set_permission({ tab_id, origin, name, state })` — pre-set a browser permission (geolocation, notifications, camera, microphone, clipboardReadWrite, clipboardSanitizedWrite, sensors) so the page API responds silently and no native prompt surfaces. Backed by `chrome.contentSettings` (not CDP `Browser.setPermission`, which would need a browser-level target unreachable from `chrome.debugger` in MV3 — see Internal notes). Scoped per-ORIGIN as a `<origin>/*` URL pattern. States map as granted→allow, denied→block, prompt→ask.

- **extension popup:** version-mismatch banner. The MCP server now stamps its `VERSION` into the `tab.registered` payload; the extension stores it on `TabState` and the popup compares it against `chrome.runtime.getManifest().version` (re-checked every 800 ms while the popup is open). When they drift the popup surfaces a red banner — _Extension X · Server Y — Reload the extension so both halves run the same code_ — plus a one-click `Open chrome://extensions` button that lands the user on the extension's own card, ready to hit the circular refresh icon. Hidden when aligned, or when no tab has registered yet. **Why it matters at this version**: 0.12.0 widens the wire protocol (new `bridge.event` message), so an extension that lags behind misses dialogs / tab-created events silently. The banner makes that visible the moment the user opens the popup.
- **catalogue:** five tools that were already wired up (`browser.claim_tab`, `browser.release_tab`, `browser.my_tabs`, `browser.events`, `browser.reset`) are now in `TOOL_CATALOGUE` so `browser-link tools disable <name>` / `enable <name>` / the Permissions menu can toggle them like the others. Previously these were always-on even when a user wanted to lock the agent out — particularly relevant for `browser.reset`, which is destructive. Catalogue is now exactly 26 tools.

### Internal

- New `bridge.event` message in the wire protocol (`ExtensionToServer` union) so the extension can push out-of-band events to the server's `BridgeEventLog`. Closed allowlist on the server side — only `dialog-opening`, `dialog-closed`, `tab-created` are accepted from the renderer; lifecycle events (`primary-elected`, `tab-registered`, etc.) stay server-owned and cannot be spoofed.
- `BridgeEventLog` is now push-based as well as pull-based. New `subscribe(fn, { replayWithinMs })` registers a listener that fires synchronously inside `add()`. Optional `replayWithinMs` replays recent events to the listener before subscribe returns — solves the race where the agent fires the action and `wait_for_tab` in the same tool batch and the source event lands in the buffer milliseconds before `wait_for_tab` registers.
- `browser.wait_for_tab` is push-based now. No polling loop, no `sinceId` snapshot. Registers a listener via `subscribeEvents` with `replayWithinMs: 1500`, resolves immediately when a matching `tab-created` lands (or comes through the replay) — `elapsed_ms: 0` is the common case.
- Auto-connect for spawned tabs: `chrome.tabs.onCreated` watches for tabs whose `openerTabId` belongs to an already-connected tab. Polls `chrome.tabs.get` up to 5 s for the new tab's `url` to surface (Chrome reports an empty `url` at the moment of `onCreated`; `connectTab` short-circuits on empty url, hence the poll), then runs the same `connectTab` flow as the popup button — debugger attach, `Page` + `Runtime` + `Log` + `Network` + `DOM` enable, WS register. Then the `tab-created` event lands on the bridge stream.
- `Page.javascriptDialogOpening` / `Page.javascriptDialogClosed` listeners in the extension's debugger handler — both emit `bridge.event` and keep a `pendingDialog` field on `TabState` for the popup to surface.
- `browser.set_permission` is backed by `chrome.contentSettings`, NOT CDP `Browser.setPermission`. Reason: `Browser.*` is a browser-level CDP domain and `chrome.debugger.attach({ tabId })` only exposes the tab-level target — the MV3 chrome.debugger API does not expose the flat-protocol `sessionId` mechanism that would let us escalate to the browser target. `chrome.contentSettings` is the surface that IS reachable, at the cost of supporting fewer permission names (the ones in the tool's enum: geolocation, notifications, camera, microphone, clipboardReadWrite, clipboardSanitizedWrite, sensors). The manifest now declares `"contentSettings"` permission.
- Popup adds a "pending dialog" UI surface with Accept / Cancel buttons (and a prompt input for `prompt` type), polling background every 800 ms while open.
- New dispatcher + event-log tests covering the three tools: forwarding, validation, claim bypass for `dialog_respond`, push-based match + replay window for `wait_for_tab`, subscriber lifecycle (in-flight, replay, no-double-fire, error isolation).

### Agent-facing gotcha

- `window.open()` triggered from a button's `onClick` handler does NOT count as a user gesture when the click was dispatched via `browser.click` (CDP `Input.dispatchMouseEvent`). Chrome's popup blocker silently swallows it (the window handle is non-null but no tab is actually created and `chrome.tabs.onCreated` never fires). The reliable way to trigger a popup-spawning click from an agent is `browser.evaluate({ expression: 'document.querySelector("...").click()' })` — `Runtime.evaluate` with `userGesture: true` (what evaluate uses internally) IS recognised as user activation. Documented in `wait_for_tab`'s `gotchas` array.

## [0.11.0](https://github.com/jobshimo/browser-link/compare/v0.10.0...v0.11.0) (2026-05-18)

### Features

- **bridge:** add `browser.wait_for` MCP tool. Blocks until a condition becomes true on the page before continuing the agent flow. Three mutually-exclusive target modes:
  - `selector` + `condition` (`visible` | `hidden` | `attached` | `detached`, default `visible`) — `visible` means the element exists in the DOM, has a non-zero bounding rect, opacity > 0, and `display !== 'none' / visibility !== 'hidden'`.
  - `expression` — any JS string evaluated each poll; `wait_for` stops as soon as `Boolean(expression)` is truthy. Runs through `Runtime.evaluate` so it is subject to the same disabled-list as `browser.evaluate`.
  - `network_url` — case-insensitive substring matched against the URL of completed network requests in the rolling buffer (last 200). Stops when at least one matching request has finished.
    Returns `{ matched, elapsed_ms, checks, reason? }`. **`matched: false` is NOT an error** — the caller decides whether to proceed or take a plan-B path. Polls every `poll_interval_ms` (default 100, clamped to `[50, 1000]`) until `timeout_ms` (default 5000, capped at 30000 — the bridge does not park requests longer than that). Like the other read tools (`browser.snapshot`, `browser.console`, `browser.network`), `wait_for` does NOT require a tab claim — multiple agents can wait on the same tab in parallel.

### Validation

End-to-end validated on the `browser-link-playground` (`/wait-for` route) with all three modes. Page-observed flip-time correlates with `wait_for`'s reported `elapsed_ms` minus the bridge dispatch latency (the parallel-call delay between `click` and `wait_for` arriving at the extension). `checks` always reflects real polling iterations, never a short-circuit.

- **ci:** hard `Version Gate` workflow — every PR to `main` is required to bump all five versioned files (root `package.json`, `packages/server/package.json`, `packages/extension/package.json`, `packages/extension/manifest.json`, `packages/shared/package.json`) in lockstep, with the new version strictly greater than `origin/main`. Mark it as a required check on `main` after this PR merges so the rule becomes truly hard.
- **ci:** `release-finalize` is now driven by the version field in `packages/server/package.json` instead of the merge commit subject. Runs as a `workflow_run` listener on the CI workflow, only when CI on `main` is green. Creates the tag and the GitHub Release through the REST API (no `git push` anywhere). Idempotent — if the release for the current version already exists, the job is a no-op.

### Refactor

- **release:** version utilities extracted to `scripts/lib/versions.mjs`, shared by `scripts/release.mjs` and the new `scripts/version-gate.mjs`. Single source of truth for the list of versioned files.

### Miscellaneous

- removed `.githooks/pre-push` and its README section. The optional interactive release reminder is gone — the strict CI gate replaces it.

## [0.5.4](https://github.com/jobshimo/browser-link/compare/v0.5.3...v0.5.4) (2026-05-12)

### Bug Fixes

- **publish:** rebuild the Chrome extension before bundling it into the npm package, and refuse to publish when the extension manifest version disagrees with `packages/server/package.json`. v0.5.3 shipped with the extension manifest stuck at `0.4.0` because `prepare-publish.mjs` only ran an `npm run build` for the extension when its `dist/manifest.json` was missing — stale builds were copied as-is. The script now always cleans the extension `dist/` and rebuilds before copying, and aborts with a clear error on any version mismatch.

## [0.5.3](https://github.com/jobshimo/browser-link/compare/v0.5.2...v0.5.3) (2026-05-12)

### Features

- **claims:** cooperative tab ownership across agents — `browser.claim_tab`, `browser.release_tab`, `browser.my_tabs`, plus `claimed_by` / `claimed_by_me` on `browser.list_tabs`. Action tools auto-claim free tabs and reject when another agent holds the tab. TTL by inactivity, auto-release on IPC disconnect, full audit trail via `browser.events` ([#32](https://github.com/jobshimo/browser-link/pull/32)).
- **extension:** redesigned popup with English copy, brand-aligned visual, pulsing status dot, gradient action button ([#30](https://github.com/jobshimo/browser-link/pull/30)).
- **updates:** in-place self-update from the setup UI — press `u` in the Updates screen to stop the running primary and run `npm install -g` automatically ([#32](https://github.com/jobshimo/browser-link/pull/32)).
- **release:** self-serve PR-based release tooling — `npm run release -- <bump>` creates a release branch + PR, finalize workflow tags and creates the GitHub Release on merge ([#32](https://github.com/jobshimo/browser-link/pull/32)).

### Security

- Cleared all open CodeQL alerts: switch-dispatch over closed tool-name union (`unvalidated-dynamic-method-call`), `assertSafeNpmName` validates the registry URL parameter (`file-access-to-http`), `sanitizeLogValue` strips control characters from IPC bridge logs (`log-injection`), removed unused imports ([#32](https://github.com/jobshimo/browser-link/pull/32)).

### Configuration

- **multi-agent + auto-reelect default ON** for fresh installs; on-disk config only carries explicit overrides ([#32](https://github.com/jobshimo/browser-link/pull/32)).

## [0.5.2](https://github.com/jobshimo/browser-link/compare/v0.5.1...v0.5.2) (2026-05-12)

- **auth:** identify WS peer by local endpoint, not socket presence ([#23](https://github.com/jobshimo/browser-link/pull/23)) — Chrome handshakes were rejected with HTTP 403 on macOS/Linux because `lookupPeerProcess` returned the server's own identity for any loopback connection. The lsof lookup now filters by local endpoint and refuses to identify the server as its own peer.
